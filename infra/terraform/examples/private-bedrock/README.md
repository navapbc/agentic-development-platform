# private-bedrock

Reference composition root that stands up the platform's AWS network, the private Bedrock path, the Fargate jumphost, and the data tier for a single account. It wires the core infrastructure modules (`vpc-endpoints`, `ecr`, `cloudtrail`, `egress`, `dns-firewall`), the application modules (`bedrock-iam`, `bedrock-jumphost-fargate`), the data tier modules (`aurora-postgresql`, `elasticache`, `clickhouse-storage`, `langfuse-blob-store`), the `secret-store` module, and the `tenant` and `tenant-config-store` modules, each tenant with its own `rebar-ticket-store`, into one apply.

It works from zero or against existing infrastructure. Set `create_network = true` to provision a tiered private VPC, or set it false and supply `vpc_id`, `subnet_ids`, `endpoint_allowed_cidrs`, and the existing tier subnets. Each core piece has its own toggle, so an account that already has VPC endpoints, a registry, an organization CloudTrail, or organization egress can skip them. The data tier services and the secret store are off until enabled.

## State

State is stored in the S3 bucket created by the [bootstrap](../../bootstrap) root, with S3 native locking. Write `backend.hcl` from the bootstrap output, or copy `backend.hcl.example` and fill in the bucket. Every `terraform init` passes it:

```
terraform init -backend-config=backend.hcl
```

A working directory that was applied before the backend existed migrates its local state once with `terraform init -migrate-state -backend-config=backend.hcl`. See the [bootstrap README](../../bootstrap/README.md).

## Usage

Copy an example tfvars file, fill in the placeholders, then apply under the platform profile. `access_log_bucket` is required and names the bucket that receives S3 server access logs from the CloudTrail, jumphost exec-log, Langfuse, and Temporal load balancer log buckets. The bootstrap root creates it and prints it with `terraform output -raw access_log_bucket`.

Greenfield, create everything:

```
cp greenfield.tfvars.example greenfield.tfvars
terraform init -backend-config=backend.hcl
AWS_PROFILE=agentic-platform terraform apply -var-file=greenfield.tfvars
```

Existing network, reuse a VPC and subnets:

```
cp existing-network.tfvars.example existing-network.tfvars
terraform init -backend-config=backend.hcl
AWS_PROFILE=agentic-platform terraform apply -var-file=existing-network.tfvars
```

## Network tiers

A created network is divided into public, application, management, and data zones. Each tier is a separate subnet group with its own route table, so a zone boundary is enforced by routing, network ACLs, and security groups rather than by convention.

| Tier | Default CIDRs | Runs | Route to the internet |
|---|---|---|---|
| Public (presentation) | `10.0.31.0/24` | The NAT instance or NAT Gateway | Internet gateway. Created only when an egress path is selected. |
| Application | `new_subnet_cidrs`, `10.0.1.0/24` | The interface endpoints and the platform services | Through the egress path |
| Management | `10.0.21.0/24` | The jumphost and the secret rotation functions | Through the egress path |
| Data | `10.0.11.0/24`, `10.0.12.0/24` | Aurora, ElastiCache, and the ClickHouse file system | None |

The data tier spans two Availability Zones because Aurora requires it. Its network ACL admits only PostgreSQL (5432), Valkey (6379), and NFS (2049) from the application and management tiers, returns responses to them, and allows traffic within the tier. The data tier has no default route, so it cannot originate a connection outside the VPC.

## Egress

`egress_mode` sets the outbound path for the application and management tiers. A created network defaults to `nat_instance`, a hardened Amazon Linux 2023 NAT instance for low-cost testing. Set `nat_gateway` for production. An existing network defaults to `none` and must keep it, because its organization supplies egress. The [egress README](../../egress/README.md) covers the hardening and the trade-offs.

A created network also enables the Route 53 Resolver DNS Firewall, which resolves only an allowlist of AWS, GitHub, Atlassian, and Slack names and answers NXDOMAIN for everything else. Add the SMTP relay with `dns_firewall_additional_domains`. The package registries that `registry_mode` adds resolve through a separate rule that trusts their CNAME chains, because they are served from CDN names that change. Set `dns_firewall_default_action = "ALERT"` to log instead of block during a trial. The `egress_public_ip` output is the address destinations see.

## Data tier

| Variable | Provisions |
|---|---|
| `create_aurora` | Aurora PostgreSQL 16.15, one Serverless v2 writer from 0 to 4 ACUs that pauses after an hour idle, with an RDS-managed rotating master secret |
| `create_cache` | ElastiCache for Valkey 9.1, one node, TLS required, with an RBAC `langfuse` user whose credential is in Secrets Manager |
| `create_clickhouse_storage` | The encrypted EFS file system and access point for the ClickHouse task |
| `create_langfuse_bucket` | The S3 bucket for Langfuse event and media uploads |

`aurora_instance_count`, `aurora_serverless_max_capacity`, and `cache_num_nodes` raise capacity and availability for production. `kms_key_arn` applies one customer managed key across the data tier, the NAT instance volume, and the log groups.

## Secret store

`create_secret_store = true` provisions the [secret-store](../../secret-store) module. It creates the platform secrets in Secrets Manager under a dedicated KMS key and adds the `secretsmanager` interface endpoint. With `create_aurora` it also enables the Aurora Data API, adds the `rds-data` endpoint, and creates the per-service database credentials with their rotation function in the management tier. One of them, `database_litellm`, is the role that owns the `litellm` database, where the EKS LiteLLM proxy keeps its virtual keys, budgets, and spend. The LiteLLM pod mounts it as `DATABASE_USERNAME` and `DATABASE_PASSWORD`, reads the Aurora writer endpoint and port from the `LITELLM_DATABASE_HOST` and `LITELLM_DATABASE_PORT` keys of the `agentic-platform-eks` ConfigMap, and verifies the server certificate and host name against the RDS CA bundle its image carries. A rotation of the secret restarts the `litellm` deployment through the eks-deployer. With `create_cache` it encrypts the cache user secret with the same key, adds the `elasticache` endpoint, and rotates the cache user.

`secret_readers` grants read access per secret to the workload roles, and `secret_restart_services` names the ECS services to redeploy after each secret changes. The module README lists the secret keys, the rotation schedule, and the manual rotation runbook.

## Rebar ticket store

Each tenant owns a [rebar-ticket-store](../../rebar-ticket-store) bucket, the bucket its rebar ticket store syncs to through `git-remote-s3`, with a dedicated KMS key and a reader and a writer role that the tenant's worker and `ticket_store.operators` may assume. `ticket_store.admins` names the principals that seed the store and empty the bucket before a destroy, and `ticket_store.writer_github_oidc_trust` lets a GitHub Actions workflow, such as the reconcile-bridge workflow, push the store through the writer role. The store reaches S3 through the S3 gateway endpoint, so it needs no interface endpoint. With the trail enabled, the root also records object-level CloudTrail data events on each bucket.

The bucket is named `<name_prefix>-<tenant>-rebar-tickets-<account ID>`, which stays the same across applies, and carries `prevent_destroy`. A deployment whose store bucket was created with a generated name, such as `<tenant>-rebar-tickets-<suffix>`, keeps it by setting `ticket_store.bucket_name` to that name before it applies this version. Otherwise the plan fails on `prevent_destroy` rather than replacing the bucket. `terraform output -json tenants` names the current bucket as `tenants.<tenant>.ticket_store.bucket`. The store roles trust the tenant's worker through an `aws:PrincipalArn` condition, so the store depends on no resource outside the tenant module and `inv aws-destroy` keeps it. Removing a tenant from `tenants` fails on `prevent_destroy` until its store is deleted, as the [rebar-ticket-store](../../rebar-ticket-store/README.md#teardown) module describes.

## Platform ECS cluster

`create_ecs_cluster = true` provisions the [ecs-cluster](../../ecs-cluster) module, the Fargate cluster the platform owns and shares with other teams. It encrypts ECS Exec sessions and Fargate ephemeral storage under dedicated KMS keys and logs Exec sessions and Container Insights to encrypted log groups. A team attaches the `ecs_deployer_policy_arn` output to its deploy role to deploy into this cluster and no other, and lists the task and execution roles that role may pass in `ecs_deployer_passable_role_arns`. A task role attaches `ecs_exec_task_policy_arn` to accept ECS Exec sessions.

## Temporal control plane

`create_temporal_control_plane = true` provisions the [temporal-control-plane](../../temporal-control-plane) module. It creates the ECR repositories for the Temporal server and admin-tools images, which `inv publish-temporal-images` fills, and the TLS secrets, which `inv temporal-certs put` fills. `temporal_frontend_acm_certificate_arn` serves the frontend from an ACM certificate, `temporal_frontend_certificate_publicly_trusted` marks that certificate as chaining to a public root, and `temporal_internode_acm_certificate_arn` tracks the internode certificate in ACM. `temporal_frontend_server_name` and `temporal_internode_server_name` name the certificates, and `inv temporal-certs put` refuses a certificate that does not carry them. `temporal_fips_140_mode` runs the Temporal processes in Go's FIPS 140-3 mode. The `temporal_tls` output lists the secrets and the expiry topic. Setting `temporal_server_image` and `temporal_admin_tools_image` to the references `inv publish-temporal-images` prints deploys the server on the platform ECS cluster, and `temporal_ui_image` with `temporal_ui_acm_certificate_arn` deploys the UI, which needs two `management_subnet_cidrs`. The root adds the server and admin-tools execution roles to the `database_temporal` readers and the server service to its restart list. Run `inv temporal-deploy` after each apply that changes an image. The `temporal_client` output holds the endpoint, namespace, server name, CA secret, and security group a worker uses, and `temporal_ui_url` the UI address. The UI load balancer admits the jumphost task group, which `inv temporal-ui` forwards through, and any CIDRs in `temporal_ui_allowed_cidr_blocks`.

`create_container_services = true` provisions the [container-services](../../container-services) module. It creates the ECR repositories for the platform, repository-intelligence, collector, Langfuse web, Langfuse worker, ClickHouse, and TLS sidecar images, and for the OPA, LiteLLM, OpenHands agent-server, buildah, semgrep, trivy, example gate engine, and catalog sandbox images the EKS pods run, which `inv publish-platform-images` fills. The `container_repository_urls` output lists them. `inv publish-platform-images`, or the `images-<arch>` artifact of the `publish-images` workflow, writes the image references, with the gate engine images in the `eks_gate_engine_images` map, to the git-ignored `images.auto.tfvars.json` in this directory, which Terraform reads with no flag. Leave the image variables out of the tfvars file, because a `-var-file` value overrides the file. `create_github_image_publisher = true` adds the [github-image-publisher](../../github-image-publisher) role that the workflow assumes to push to those repositories, trusting `github_repository` on `github_publish_refs`. Set `github_repository_ids` to the owner and repository IDs when the repository's OIDC tokens carry GitHub's immutable subject. Set `github_oidc_provider_arn` to the account's existing GitHub provider, or leave it empty to create one, and read the role from the `github_image_publisher_role_arn` output. `container_internal_acm_certificate_arn` adds the internal load balancer that names coordination, repo-intelligence, the collector, and Langfuse under `container_internal_domain`, which needs two `new_subnet_cidrs`. `container_internal_allowed_cidr_blocks` admits networks beyond the client security group, and the `container_internal_endpoints` output lists the groups, target groups, and URLs.

With the internal load balancer, `container_platform_image`, `container_repo_intelligence_image`, and the Temporal control plane, the module also runs the platform services on the cluster: the workflow and review workers, each in a blue and a green slot, coordination, repository intelligence, and the index worker, with the `db-migrate` and `schedule-bootstrap` one-shot tasks. `container_config_dir` names the directory of the environment's config files, which the tasks receive as `PLATFORM_ENV_CONFIG`, and `container_platform_ca_file` the CA the clients trust for the internal names. The composition lists each execution role as a reader of the secrets it injects and of the Temporal CA, attaches `bedrock_invoke_policy_arn` to the review worker, and adds the `bedrock-runtime-fips` interface endpoint when `container_use_fips_endpoints` is true. `inv platform-deploy` reads the `container_deploy` output, and the `container_workspace` output lists the workspace file system and its access points.

With `create_cache`, `create_clickhouse_storage`, `create_langfuse_bucket`, the secret store, and the four `container_langfuse_web_image`, `container_langfuse_worker_image`, `container_clickhouse_image`, and `container_tls_sidecar_image` references, the module also runs Langfuse web and worker against the `langfuse` database role, the cache user, and the blob bucket, and ClickHouse on the `clickhouse-storage` file system. `container_langfuse_admin_email` names the administrator, `container_langfuse_public_url` the URL `inv langfuse-ui` forwards, and `container_langfuse_task_sizes` the task sizes. The composition admits the jumphost task group to the internal load balancer, adds the Langfuse and ClickHouse services to the secret store restart rules for the secrets they read, and lists only the workloads that connect to Temporal as readers of the Temporal CA. The `container_clickhouse` output names the secret `inv clickhouse-certs put` writes, and the `container_langfuse` output the Langfuse URLs.

`container_collector_image` with `container_tls_sidecar_image` runs the collector, and every platform task exports to it. With `container_collector_exports_enabled`, the default, the composition adds the `xray-fips` or `xray` and the `aps-workspaces` interface endpoints, the collector exports to X-Ray and to a Prometheus workspace, and with Langfuse it forwards the generation spans to Langfuse. `container_xray_encryption_enabled` sets the region's X-Ray encryption to the telemetry key, which changes it for every X-Ray user in the region. The `container_telemetry` output names the workspace and its endpoint.

`create_managed_grafana = true` provisions the [managed-grafana](../../managed-grafana) module over the collector's Prometheus workspace and X-Ray traces, and needs the collector exports. The workspace signs users in through IAM Identity Center, grants the Grafana Admin, Editor, and Viewer roles to the groups in `grafana_admin_group_ids`, `grafana_editor_group_ids`, and `grafana_viewer_group_ids`, and connects to the application subnets, so its data source traffic reaches Prometheus and X-Ray through the interface endpoints. The composition adds the `aps-workspaces`, `grafana-workspace`, and `xray` interface endpoints. The workspace role holds the Prometheus query actions itself. With `grafana_query_principal_arns` set, the module also creates a query role that may only query the Prometheus workspace and that only those principals may assume, and with the list empty it creates none. `grafana_private_access` admits only the `grafana-workspace` endpoint to the workspace. The `managed_grafana` output holds the workspace URL, the query role when it exists, and the settings a Grafana Admin enters once for the two data sources, which the module README lists. With `create_managed_grafana` false, the default, the composition creates no workspace, role, key, group, or endpoint for it.

`off_hours_enabled` provisions the [off-hours](../../off-hours) module for the platform and Temporal ECS services. The Temporal server and UI, ClickHouse, and the collector stop last and start first. `off_hours_timezone`, `off_hours_sleep_schedule`, and `off_hours_wake_schedule` set the window, and the `off_hours` output names the documents for a run outside the schedule. The composition also lists every service and worker slot under each secret it reads in the secret store restart rules, so a rotation redeploys all of its consumers.

## EKS cluster

`create_eks = true` provisions the [eks-cluster](../../eks-cluster) module in the application subnets, with the API endpoint private to the VPC and open on 443 to the jumphost task group only. Each principal in `eks_admin_principal_arns`, keyed by a static label, receives cluster admin through an access entry. `eks_kubernetes_version`, `eks_platform_node_group`, `eks_sandbox_node_group`, and `eks_addon_versions` pass through to the module, and `container_use_fips_endpoints` sets the Secrets Store CSI provider to the Secrets Manager FIPS endpoint. Create the cluster with `eks_network_policy_enforcing_mode = "standard"`, run `inv eks-deploy`, and set `strict` once it reports that every pod is selected by a NetworkPolicy, as the module README describes.

The composition creates Pod Identity roles for the `litellm` and `inbound-webhook` service accounts of the platform namespace and for each tenant's `activity-worker` service account, and lists each as a reader of the secrets its pods mount. The platform namespace runs no MCP gateway, and each tenant's MCP gateway runs as the tenant's `activity-worker` service account. It attaches `bedrock_invoke_policy_arn` to the litellm role, adds the tenant worker and inbound webhook roles to the Temporal CA readers, and lets the EFS CSI node driver mount each tenant's workspace access point through a policy limited to those access points. Each tenant worker role may issue ECR tokens and pull from every platform catalog repository, which covers the scanner, gate engine, OpenHands agent server, checks, and buildah images, from each repository in `eks_gate_image_repository_arns`, and from the pull-through cache repositories of `registry_mode`, because the gate, checks, scanner, and image verification pods pull their images with the token it requests. The workspace mount targets admit the cluster security group, which the nodes carry. Aurora, the cache, and ClickHouse admit the application subnets, which hold the pod addresses. A pod reaches the Temporal frontend and the internal load balancer through a SecurityGroupPolicy that attaches the Temporal and internal client groups, which the `eks` output names.

The root also adds the `eks-auth` interface endpoint and its name to the DNS Firewall allowlist, so the Pod Identity agent obtains credentials inside the VPC, and tags the public subnets with `kubernetes.io/role/elb` and the application subnets with `kubernetes.io/role/internal-elb` for the Load Balancer Controller. An internet-facing load balancer spans two Availability Zones, so `create_eks` needs two `public_subnet_cidrs`. The `eks` output holds the cluster name, endpoint, VPC, Pod Identity roles, security groups, workspace file system and access point, node scheduling label and taint, controller settings, and control plane log group. `platform_environment` holds the environment the ECS platform tasks receive and `environment_config` the environment's config files, for the `agentic-platform-env` and `platform-config` ConfigMaps of the [AWS overlay](../../../../deploy/kubernetes/README.md#the-aws-overlay). `eks_webhook_certificate_arn`, `eks_mcp_gateway_certificate_arn`, and `eks_mcp_gateway_client_cidrs` pass through to the output for the inbound webhook Ingress and the Ingress of each tenant's MCP gateway. With `eks_mcp_gateway_certificate_arn`, each tenant's gateway gets its own internal ALB that admits `eks_mcp_gateway_client_cidrs` and serves the host `mcp-<tenant>.<eks_mcp_gateway_domain>`, which the tenant's `mcp_gateway_host` may replace with another `<label>.<eks_mcp_gateway_domain>`. The gateway Ingress rule and `MCP_ALLOWED_HOSTS` name that host, and the `eks` output lists each tenant's host in `mcp_gateway_hosts`. The root creates a private hosted zone for `eks_mcp_gateway_domain` in the VPC and adds `*.<eks_mcp_gateway_domain>` to the DNS Firewall allowlist unless the domain ends in `.internal`. The domain may not be `container_internal_domain`, because a VPC takes one private hosted zone per name. The certificate must cover every tenant's host, such as with `*.<eks_mcp_gateway_domain>`, and the plan refuses the ARN of `eks_webhook_certificate_arn`, whose certificate names the load balancer instead. In an environment without a public domain, sign it with the platform CA and import it with `inv mcp-gateway-certs issue --dir DIR --domain <eks_mcp_gateway_domain>` and `inv mcp-gateway-certs import --dir DIR`, where DIR holds the `ca.pem` of `inv temporal-certs generate --internal-name`, such as `~/.agentic-platform/internal-tls-sandbox`. Set `eks_mcp_gateway_certificate_arn` to the ARN it prints, apply, and run `inv eks-deploy`. A later import re-imports into that ARN. See [Issuing the MCP gateway certificate](../../../../deploy/kubernetes/README.md#issuing-the-mcp-gateway-certificate-in-an-environment-without-a-public-domain). Terraform cannot read the names of a certificate from its ARN, so `inv eks-deploy` checks them with `acm:DescribeCertificate` and refuses a certificate that misses a host before it starts the task. The AWS Load Balancer Controller creates each ALB after the apply, so once the deploy task succeeds `inv eks-deploy` finds each tenant's ALB by its `elbv2.k8s.aws/cluster` and `ingress.k8s.aws/stack` tags and upserts an alias record for the tenant's host in the zone with the operator's credentials, which need `acm:DescribeCertificate`, `elasticloadbalancing:DescribeLoadBalancers`, `elasticloadbalancing:DescribeTags`, and `route53:ChangeResourceRecordSets` on the zone. The deploy task has no route to the Route 53 API, and its role holds no AWS permission. The zone sets `force_destroy`, so a destroy deletes the records Terraform does not track. A client outside the VPC resolves the zone only through a Route 53 Resolver inbound endpoint or an association with its own VPC. `temporal_ca_secret_arn` names the Temporal CA the overlay mounts. Its `images` map names the platform, OPA, and LiteLLM images from `images.auto.tfvars.json`, and its `image_settings` map sets `OPENHANDS_AGENT_SERVER_IMAGE`, `GATE_ENGINE_BUILDER_IMAGE`, `SEMGREP_IMAGE`, and `TRIVY_IMAGE` for the activity worker to the ECR copies, so the pods it creates pull from ECR, `GATE_ENGINE_IMAGES` to the `eks_gate_engine_images` map, which image-mode gate engines run, and `RUNTIME_IMAGES` to the `eks_runtime_images` map, which runtime profiles name as `catalog:<name>`.

### Registries for the gate, checks, and scanner pods

DNS Firewall resolves no public container or package registry, so the base images a gate engine or a repository's checks start from, and the packages a checks command installs, need a source inside the boundary. `registry_mode` selects it.

| Mode | Images | Packages | Gate pod egress on 443 |
|---|---|---|---|
| `none` | ECR repositories only | None | The application subnets and the S3 ranges |
| `aws` | ECR pull-through caches of ECR Public, Quay, and `registry.k8s.io`, plus Docker Hub and GHCR when listed in `registry_upstream_credentials` | The public indexes in `registry_package_domains` | Also every address outside the VPC |
| `external` | An Artifactory or compatible service that `config/<env>/registries.yaml` names | The same service | Also `registry_external_cidrs` |

In `aws` mode the composition creates a pull-through cache rule and a repository creation template per upstream under `<name_prefix>-<upstream>`, generates `registries.yaml` into the `platform-config` ConfigMap, adds `registry_package_domains` to DNS Firewall, and lets the activity worker role fill the caches. The template sets no resource tags, because ECR needs a custom repository creation role to tag a repository it creates for a pull-through cache, and the first pull of an image fails without one. `docker.io/library` maps to the ECR Public copy of the Docker official images, which needs no Docker Hub credential. `public.ecr.aws` itself maps to the same cache, so a Dockerfile `FROM public.ecr.aws/docker/library/python` line resolves through it. Each upstream in `registry_upstream_credentials` gets an `ecr-pullthroughcache/<name_prefix>-<upstream>` secret, which an operator fills with JSON holding `username` and `accessToken`. DNS Firewall stops a pod that resolves any name outside its allowlist, and a pod that connects to a literal address outside the VPC is the residual exposure of this mode.

In `external` mode the operator writes `registries.yaml` from [registries.yaml.example](../../../../config/local/registries.yaml.example) into `container_config_dir`, sets `registry_external_host` and `registry_external_cidrs`, and puts a read-only token in the `registry_token` secret, which the activity worker mounts as `REGISTRY_TOKEN`. The gate pods reach only the registry, so this mode keeps the tighter boundary.

Both modes serve package installs over HTTPS only. Debian and Ubuntu base images fetch their OS packages over plain HTTP, which neither mode admits, so a gate engine runs from an image published with its OS packages installed rather than from a build of its Dockerfile in the pod.

### EKS deploy

With the ECS cluster and the container services, `create_eks` also provisions the [eks-deployer](../../eks-deployer) task in the management tier. Its task definition carries the `eks_deployer_image` from `images.auto.tfvars.json` and the render inputs the composition computes: the images, the security groups, the workspace volume handle, the ticket store roles, the secret ARNs, the VPC, service, application subnet, and S3 ranges, and the ingress settings. Its role reaches the API through an access entry with cluster admin, and its group is admitted to the API endpoint. `inv eks-deploy` runs it, and the `eks` output's `deployer` names the task. `eks_load_balancer_controller_image_repository` overrides the regional EKS registry the controller image comes from.

With the secret store, the `eks_deployer_image`, and either Aurora or at least one tenant, the secret store's restart rules also start the task. With Aurora, a change of the `database_platform_app` secret runs `restart tenant-workers inbound-webhook mcp-gateway`, where `mcp-gateway` names every tenant's MCP gateway, so the EKS pods that hold a database connection, every tenant's activity worker among them, read the rotated password. For each tenant, a `restart_eks.external_secrets` entry restarts `tenant-<tenant>/activity-worker` and `tenant-<tenant>/mcp-gateway` after the tenant's repository intelligence token rotates or an operator updates it, so both mount the new token. The tenant worker and inbound webhook roles decrypt the Temporal CA through an identity policy, because the Temporal key admits its readers through IAM.

## Tenants

Teams share the deployment as tenants. A tenant is a trust boundary, a set of credentials and everything that may see them, and teams that share credentials share a tenant. `tenants` maps each tenant name to its entry, and `create_eks` needs at least one entry, because every run belongs to a tenant and the deployment has no default tenant. The name `default` is refused. [tenants.tfvars.example](tenants.tfvars.example) defines a platform tenant and Java, Python, and ReactJS tenants.

For each tenant the root creates the following.

- A Pod Identity role, `<cluster>-tenant-<tenant>`, bound to the `activity-worker` service account of the `tenant-<tenant>` namespace, with the [tenant](../../tenant) module's worker policy attached.
- The resources of the tenant module, which are its key, its secrets under `<name_prefix>/tenants/<tenant>/`, its ECR prefix `<name_prefix>/tenants/<tenant>` with repositories created on the first push, its config publisher role when `config_repository` is set, and its rebar ticket store.
- A workspace access point rooted at `/tenants/<tenant>` on the workspace file system, which the EFS CSI node role may mount.
- A generated repository intelligence token, `<name_prefix>/tenants/<tenant>/repo-intelligence-token`, which the tenant worker receives as `REPO_INTELLIGENCE_TOKEN`. Repository intelligence receives the token's ARN in `REPO_INTELLIGENCE_TOKEN_SECRET_ARNS` and reads its current and previous versions with its task role at runtime. Only the worker role, the repository intelligence task role, and the token rotation role may read it. The secret store's token rotation function, which the root creates with the pattern `<name_prefix>/tenants/*/repo-intelligence-token` in `rotated_token_secrets`, rotates it every 30 days, and the secret store's restart rule then restarts the tenant's activity worker and MCP gateway through the eks-deployer.
- A generated MCP gateway token, `<name_prefix>/tenants/<tenant>/mcp-gateway-token`, which only the worker role and the tenant's `mcp_gateway_token_readers` may read. An operator in `mcp_gateway_token_readers` reads it with `aws secretsmanager get-secret-value` and gives it to the tenant's MCP clients. The tenant's own MCP gateway in `tenant-<tenant>` mounts it as `MCP_GATEWAY_TOKEN`, and the gateway of another tenant refuses it.
- With two or more tenants, the tenant's GitHub and Jira webhook signing secrets, `<name_prefix>/tenants/<tenant>/github-webhook-secret` and `<name_prefix>/tenants/<tenant>/jira-webhook-secret`, created empty, which only the inbound webhook role may read. `tenant_webhooks.tf` attaches one policy for every tenant to that role, so the role holds two managed policies whatever the tenant count. The policy reads the secrets named `<name_prefix>/tenants/*/github-webhook-secret` and `<name_prefix>/tenants/*/jira-webhook-secret`, decrypts them with each tenant's key through Secrets Manager, and lists and reads `tenants/*` of the config bucket. It holds about 1700 characters plus one key ARN of up to 90 characters per tenant, so it fits the 6144 character limit of a managed policy up to about 50 tenants, and a plan that exceeds the limit fails its precondition. The EKS deploy mounts both secrets into the inbound webhook and sets `TENANT_CONFIG_BUCKET` on it.
- Read access to each secret store key in `shared_secrets`, for a credential the tenant shares with the platform or with another tenant, and to the platform secrets every worker reads, which are `database_platform_app`, `coordination_shared_secret`, `litellm_master_key`, `review_attestation_secret`, and the Temporal CA.
- The sandbox image pull, pull-through cache fill, and Temporal CA policies on its worker role.

`secrets` defaults to `github_token`, `jira_api_token`, `jira_pat`, `authorship_signing_key`, `registry_token`, and `slack_webhook_url`. Each secret is named `<name_prefix>/tenants/<tenant>/<name>` with the underscores of `<name>` replaced by hyphens, such as `agentic-platform/tenants/claims/github-token`. Fill each with `aws secretsmanager put-secret-value --secret-id <secret name>`. A tenant's `config_repository` needs the account's GitHub OIDC provider, from `github_oidc_provider_arn` or `create_github_image_publisher`. The [tenant-config-store](../../tenant-config-store) bucket holds every tenant's bundle under `tenants/<tenant>/`, and `tenant_config_admin_principals` may restore or empty it. Each tenant's bundle readers are its worker role, which carries the bucket's `tenant-config-reader` principal tag with the tenant name, its publisher role, which carries the `tenant-config-publisher` tag, and the bucket's `shared_readers`, which are the task roles of repository intelligence, the index worker, and the review worker, and with two or more tenants the inbound webhook role. The three task roles receive the bucket name as `TENANT_CONFIG_BUCKET`, read every tenant's bundle, and decrypt with the config store key. Repository intelligence and the index worker read each tenant's checkouts under `/tenants/<tenant>/repositories`. The trail records object-level events on that bucket and on each tenant's ticket store. The `tenants` output names each tenant's role, namespaces, secrets, prefixes, publisher role, ticket store, and workspace access point.

`container_platform_settings` sets environment values every platform task and EKS worker receives, such as `TICKET_BACKEND`, for settings that are the same for every tenant. A name that contains KEY, TOKEN, SECRET, PASSWORD, or PAT is refused, because a secret belongs in the secret store, and so is a name the container-services module sets. The module sets `TENANTS` to the tenant names, so the workflow worker polls each tenant's task queue.

A tenant's `settings` reach only that tenant's worker and override `container_platform_settings`, for example `TICKET_BACKEND = "jira"` for a tenant whose tickets live in Jira. The same name rules apply, and `TENANT`, `TENANTS`, `TENANT_CONFIG_BUCKET`, and the namespaces and paths the deployment derives from the tenant name are refused. `sandbox_quota` sets the hard limits of a ResourceQuota on the tenant's sandbox namespace, such as `"requests.cpu" = "16"` or `pods = "40"`. `MAX_CONCURRENT_RUNS` in `settings` caps the tenant's runs in flight, 4 when unset, because each worker counts and admits only its own tenant's executions. No setting counts sandboxes on their own. The `pods` hard limit caps every pod of the sandbox namespace at once, the agent sandbox, gate engine, checks, and CI repair pods together.

A tenant's `model_limits` sets the LiteLLM limits its runs work under. The worker receives each value as an environment variable and applies it to the tenant's LiteLLM team and to the virtual key it creates for each run. Terraform creates no LiteLLM object. The worker creates the team, whose ID is the tenant name, before the first stage that starts a sandbox, CI repair, or gate engine pod, and updates it when the limits change. Each value is 0 or greater, `rpm_limit` and `tpm_limit` are whole numbers, and the four variable names are refused in `settings`.

| Attribute | Worker variable | Default | Meaning |
|---|---|---|---|
| `monthly_budget_usd` | `TENANT_MODEL_BUDGET_USD` | 0 | The tenant team's spend limit per month in US dollars. 0 sets no team budget. |
| `rpm_limit` | `TENANT_MODEL_RPM_LIMIT` | 0 | The tenant team's requests per minute. 0 sets no limit. |
| `tpm_limit` | `TENANT_MODEL_TPM_LIMIT` | 0 | The tenant team's tokens per minute. 0 sets no limit. |
| `run_budget_usd` | `RUN_MODEL_BUDGET_USD` | 10 | The spend limit of each run's virtual key in US dollars. |

The EKS deploy renders, for each tenant, the `tenant-<tenant>` namespace with the tenant's activity worker, its MCP gateway with a Service and, with `eks_mcp_gateway_certificate_arn`, an internal ALB Ingress, its secret provider, its ticket store profiles, and its workspace claim at `/tenants/<tenant>`, and the `tenant-<tenant>-sandbox` namespace with the agent, gate, checks, and scanner pod permissions. The review worker mounts the `/tenants` root read-only at the same path, so it reads each tenant's checkouts where the tenant's worker wrote them. Each tenant's worker installs its own intake and reap schedules on its task queue, `agent-platform-<tenant>`, when it starts, and the `schedule-bootstrap` task removes the schedules of a deployment without tenants.

### Onboarding a tenant

A team that shares credentials with an existing tenant joins that tenant and needs no new entry. A team whose repositories use another language joins its tenant as well, because the language of a repository is its runtime profile, which the tenant's [config bundle](../../../../docs/tenant-config.md) assigns, as [runtime profiles](../../../../docs/runtime-profiles.md) describes. A new entry is for a team with its own credentials.

1. Add the entry to the `tenants` map. Copy [tenants.tfvars.example](tenants.tfvars.example) to `tenants.auto.tfvars`, which Terraform loads with no flag, so `inv aws-release` and `inv aws-destroy`, which pass one var file, read the map too. A `tenants` value in the environment's tfvars file would override it, so set the map in one file only. The name matches `^[a-z][a-z0-9]{1,15}$`. The entry takes the attributes below.

   | Attribute | Required | Meaning |
   |---|---|---|
   | `description` | Yes | What the tenant holds, shown in the `tenants` output. |
   | `secrets` | No | The secret store keys the tenant owns, the six names above by default. |
   | `shared_secrets` | No | Keys of the platform secret store the tenant's worker may also read. |
   | `config_repository` | No | `github_repository` as `<owner>/<repo>`, `allowed_refs`, `["refs/heads/main"]` by default, where a trailing `*` matches a prefix, and `github_repository_ids` with `owner_id` and `repository_id`, set when the repository's OIDC tokens carry GitHub's immutable subject, which names the numeric IDs. Without it the tenant has no publisher role. |
   | `ticket_store` | No | `bucket_name` to keep an existing bucket, `operators` and `admins` of the tenant's rebar ticket store, and `writer_github_oidc_trust` for a CI workflow that writes tickets, as the [rebar-ticket-store](../../rebar-ticket-store) module describes. |
   | `mcp_gateway_host` | No | The host name of the tenant's MCP gateway, `<label>.<eks_mcp_gateway_domain>`. `mcp-<tenant>.<eks_mcp_gateway_domain>` by default. |
   | `settings` | No | Environment values for the tenant's worker only, such as `TICKET_BACKEND` or `MAX_CONCURRENT_RUNS`. |
   | `model_limits` | No | `monthly_budget_usd`, `rpm_limit`, `tpm_limit`, and `run_budget_usd`, as the table above lists. |
   | `sandbox_quota` | No | The ResourceQuota hard limits of the tenant's sandbox namespace. |

2. Plan and apply the root with `terraform plan -var-file=<environment>.tfvars -out=tfplan` and `terraform apply tfplan`. Read the tenant's resources with `terraform output -json tenants`, whose `tenants.<tenant>` entry names `publisher_role_arn`, `config_prefix`, `image_prefix`, `secret_arns`, `signing_profile`, `namespace`, `sandbox_namespace`, `ticket_store`, `worker_role_arn`, and `workspace_access_point`, and whose `config_bucket` names the tenant config bucket.
3. Fill the tenant's secrets with `aws secretsmanager put-secret-value --secret-id <name_prefix>/tenants/<tenant>/<name> --secret-string <value>`, using the hyphenated names. A secret left without a value is omitted from the worker's mount at the next deploy. With two or more tenants, fill `github-webhook-secret` and `jira-webhook-secret` with the values the tenant's GitHub and Jira webhooks sign with, because the inbound webhook refuses the tenant's deliveries until they hold a value.
4. Grant the config repository's workflow the `id-token: write` permission and set the `publisher_role_arn` output as the role it assumes through GitHub OIDC. The role trusts tokens whose audience is `sts.amazonaws.com` and whose subject is `repo:<owner>/<repo>:ref:<ref>` for a ref in `allowed_refs`, or `repo:<owner>@<owner_id>/<repo>@<repository_id>:ref:<ref>` with `github_repository_ids`. It may list, write, and delete objects under `tenants/<tenant>/` of the config bucket, push images under the tenant's ECR prefix, and sign with the tenant's Signer profile. It cannot read the bundle objects.
5. Publish the first bundle from the config repository's workflow with `inv tenant-config-publish --tenant <tenant> --bundle-dir <bundle> --bucket <config_bucket> --environment-dir <copy of config/<environment>>`, as [publishing](../../../../docs/tenant-config.md#publishing) describes. Publish it before the tenant's worker first starts, because a worker whose first bundle fails validation refuses to start.
6. Deploy the platform tasks and the EKS workloads with `inv platform-deploy` and `inv eks-deploy`, or with `inv aws-release`, which applies the root and then deploys both. The workflow worker begins polling `agent-platform-<tenant>`, and the tenant's worker installs its intake and reap schedules. After a later secret change, `inv eks-deploy --command "restart tenant-workers"` restarts the tenant workers.
7. Check the tenant boundary with `inv tenant-verify-aws --context <eks context>`, which reads `terraform output -json`, or the file `--outputs` names, and runs read-only checks. `iam` simulates each tenant secret's resource policy and the tenant and config keys, `env` lists the variable and mounted file names, never the values, of every tenant container and flags another tenant's names, `ri` probes repository intelligence from each activity worker for 401 without a token, 403 for another tenant's repository, and 200 for its own, and `mounts` checks the workspace and bundle mounts. `--only iam,env,ri,mounts` selects checks, `--repo <tenant>=<repository>` names the repository to probe, and `--region` and `--admin-role-arn` override the defaults. The task prints PASS, FAIL, or SKIP per check and exits 1 on any FAIL and 2 on a setup error. kubectl needs a route to the private EKS API, and the ECS checks need `container_enable_execute_command = true` and the session-manager-plugin and report SKIP without them.
8. For the first tenant of a payer account, activate the `tenant` cost allocation tag as [cost attribution](#cost-attribution) describes. Activation covers every value of the key, so a later tenant needs no step.

### Cost attribution

The tenant module tags each resource it creates with `tenant = <tenant>`, and the root tags each tenant's workspace access point the same way. AWS Billing splits the bill by that tag only after the tag is activated as a cost allocation tag, once per payer account. The tag key appears in the Billing console only after a tagged resource exists, and a newly activated tag can take up to 24 hours to appear in Cost Explorer and the Cost and Usage Report. Activation applies from that point forward and does not tag earlier usage.

1. Apply the root with at least one tenant, so the `tenant` tag key exists on a resource.
2. Activate the key from the payer account with `aws ce update-cost-allocation-tags-status --cost-allocation-tags-status TagKey=tenant,Status=Active`, or under Billing and Cost Management, Cost allocation tags, User-defined cost allocation tags.
3. Confirm it with `aws ce list-cost-allocation-tags --tag-keys tenant --type UserDefined`, which reports `Status` as `Active`.
4. Group Cost Explorer or the Cost and Usage Report by the `tenant` tag.

The tag splits the tenant's own resources, which are its key, secrets, image repositories, ticket store bucket, and workspace access point. Model spend does not carry it, because LiteLLM calls Bedrock under one role for every tenant. LiteLLM attributes model spend to the tenant instead, through the tenant's team and the `tenant:<tenant>` tag on every request, and `inv cost-rollup --tenant <tenant>` reports a tenant's recorded model spend per execution.

### Image governance

The root writes `image_policy.yaml` into the platform config the EKS deploy renders. It admits the catalog repositories, each tenant's prefix under `<name_prefix>/tenants/<tenant>/`, the pull-through caches, and `image_policy_registries`, and each tenant's sandbox namespace receives the same list for its admission policy. It also creates an AWS Signer profile for the platform, whose ARN the `image_signing_profile_arn` output names, and one per tenant, which only the tenant's publisher role may sign with.

`image_scanning_enabled` enables Amazon Inspector for ECR and sets the account's registry scanning to enhanced and continuous for every repository, which is an account setting billed per image scanned. Each tenant worker then reads an image's scan before a pod pulls it and refuses an image with an active finding at `image_finding_severity` or above, `HIGH` by default, unless an entry of `platform/image_exceptions.yaml` or the tenant's bundle `image_exceptions.yaml` in the tenant config bucket accepts it. The `image-exception` workflow adds platform entries, the daily review in `publish-images` removes expired and resolved ones, and the plan fails when `container_config_dir` holds `image_exceptions.yaml`. Set the `config_bucket` output as the `AWS_CONFIG_BUCKET` repository variable and the `github_image_exception_role_arn` output as `AWS_IMAGE_EXCEPTION_ROLE_ARN`. `image_signature_verification` verifies each catalog and tenant image's signature before the pull, runs the pull pods as an `image-verifier` ServiceAccount bound to a role allowed only `signer:GetRevocationStatus`, adds `verification.signer.<region>.amazonaws.com` to the DNS Firewall allowlist, and lets the pull pods reach addresses outside the VPC on 443 for the revocation check. See [image governance](../../../../docs/image-governance.md).

## After apply

1. Push the jumphost image to the repository shown in the `jumphost_ecr_repository_url` output with `inv publish-jumphost-image --tag v1`, where the tag matches `jumphost_image_tag` and is not yet in the repository. It scans the image and signs it with the `image_signing_profile_arn` profile inside the buildah image that `inv publish-platform-images` pushes, so run it after that task, or pass `--unsigned` when the root creates no signing profile. See the [bedrock-jumphost-fargate README](../../bedrock-jumphost-fargate/README.md#image-delivery).
2. Attach the `bedrock_invoke_policy_arn` output to any workload role outside the composition that signs Bedrock inference. The composition attaches it to the review worker.
3. Bring up the platform and open the tunnel with `inv tunnel-start --detach`.
4. With the secret store and Aurora enabled, create the per-service database roles before the first migration with `inv db-bootstrap-roles --function-name "$(terraform output -raw role_bootstrap_function_name)"`. Run it again after an apply that adds a role, such as `litellm`, to an existing cluster, before the next `inv eks-deploy`. Then set each external secret, such as `github_token`, with `aws secretsmanager put-secret-value`.
5. With `create_managed_grafana`, a member of a `grafana_admin_group_ids` group signs in at the `managed_grafana.workspace_url` output and adds the Prometheus and X-Ray data sources from `managed_grafana.data_sources`, as the [managed-grafana](../../managed-grafana/README.md#data-sources) README describes.

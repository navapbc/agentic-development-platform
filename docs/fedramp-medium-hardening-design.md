# FedRAMP Medium hardening design

This design ties each platform component to the FedRAMP Medium control families it satisfies, grounded in the controls the platform implements today. It is a design reference. It provisions nothing and changes no runtime code. The platform-owned controls that are not yet met are tracked as dedicated v0.3.0 features in the [roadmap](../ROADMAP.md), not in this document.

Control family labels follow NIST SP 800-53 Revision 5. A mapping to a family cites the terraform module or the code that implements the control, so the posture is verifiable rather than aspirational. The companion [local-to-AWS mapping](local-to-aws-mapping.md) records where each component runs in a deployed environment.

## Trust boundary and deployment posture

The platform runs inside the target VPC. It reaches the private `bedrock-runtime` interface endpoint with the direct connectivity provider and no hop, and it has no public ingress except the webhook receiver, which authenticates every request. Private reachability comes from the shared interface and gateway endpoints in the [vpc-endpoints](../infra/terraform/vpc-endpoints) module, whose security group admits port 443 only from in-VPC subnets. This establishes the boundary the SC family protects.

## Control inheritance

The platform is hosted on an AWS account that holds a FedRAMP Medium authorization. Under the FedRAMP shared-responsibility model the platform inherits the controls AWS owns and implements the controls it configures on top. The physical and environmental families, the hypervisor and host controls, the FIPS-validated cryptographic modules behind KMS and the FIPS service endpoints, the durability and availability of the managed services, and the underlying network fabric are inherited from the AWS authorization. The platform is responsible for how it configures and uses those services, which is encryption enabled, least-privilege IAM, audit logging turned on, retention set, network isolation applied, FIPS endpoints selected, and secrets managed. The control inheritance and shared-responsibility matrix in [fedramp-control-inheritance.md](fedramp-control-inheritance.md) records the per-family split of inherited, platform-implemented, and deploying-organization controls. The sections below describe the platform-implemented portion. The platform-owned controls that are not yet met are tracked as v0.3.0 features in the [roadmap](../ROADMAP.md).

## Temporal control plane

Posture. The Temporal server runs as a Fargate service on the platform ECS cluster in the application tier, with no public address. Clients reach the frontend through an internal NLB that admits port 7233 only from the Temporal client security group, and the server tasks admit the frontend only from the NLB and the internode ports only from each other. The frontend serves TLS, and the internode listeners require mutual TLS with a certificate from the configured CA and refuse any other peer. The frontend certificate comes from a CA the platform generates, from the deploying organization's PKI, or from ACM. When it comes from ACM, the NLB terminates the client connection under the `ELBSecurityPolicy-TLS13-1-2-FIPS-2023-04` policy, which negotiates TLS 1.2 and 1.3 only, and re-encrypts to the server. The certificates and keys live in Secrets Manager under a dedicated KMS key, never pass through Terraform, and are readable only by the execution roles of the tasks that use them. Only the server reads a private key. The server and the admin-tools task connect to Aurora over TLS with host verification against the RDS CA bundle, whose SHA-256 the image build pins, using the `temporal` role from the secret store, and a rotation of that password redeploys the server. The admin-tools task applies the schemas before any server of a new version starts. The UI runs in the management tier behind an internal HTTPS ALB under the same FIPS policy, which admits only the jumphost task group and the listed operator networks, and it connects to the frontend over TLS with host verification. Every container runs as a non-root user on a read-only root file system, except an init container that runs as root to make the scratch volume writable and then exits. The task definitions hold secret ARNs and no secret values. The images are built from upstream images pinned by digest and pushed to KMS-encrypted ECR repositories with immutable tags and scan on push. Task logs go to CloudWatch log groups under the module's KMS key, and both load balancers write access logs to a TLS-only bucket. ECS Exec into the Temporal tasks is off unless enabled.

Controls. SC-7 boundary protection through the internal load balancers, the client and server security groups, and the tier placement in [temporal-control-plane](../infra/terraform/temporal-control-plane). SC-8 and SC-8(1) through TLS on the frontend and the UI, mutual TLS between the server tasks, and TLS with host verification to Aurora. SC-13 through the FIPS security policies on both load balancers and, with `fips_140_mode` enabled, Go's FIPS 140-3 mode in the server, admin-tools, and UI processes, which refuses non-approved algorithms such as ChaCha20-Poly1305 and X25519 on the frontend and internode listeners. SC-12 through the dedicated KMS key for the TLS secrets and the ACM expiry events routed to an SNS topic. SC-28 through KMS encryption of the secrets, the log groups, and the image repositories. IA-5(2) public key-based authentication through the internode certificate check. AC-3, AC-4, and AC-6 through the client security group, the per-secret reader policies, and the per-task execution roles. AU-2, AU-11, and AU-12 through the task logs and the load balancer access logs with their retention. CM-2, CM-6, and CM-7 through the pinned images, the managed dynamic configuration that refuses the removed Worker Versioning V1 keys, and the read-only root file systems. RA-5 through scan on push.

Cryptographic module. `fips_140_mode` sets `GODEBUG=fips140=on`, which enforces FIPS-approved algorithms. Every Go binary in the server, admin-tools, and UI images is built from source with `GOFIPS140=v1.0.0`, which selects the CMVP-certified Go Cryptographic Module snapshot `v1.0.0-c2097c7c`, so the TLS the server terminates in secrets mode, the internode mutual TLS, and the UI connection to the frontend run on that module. `go version -m` on each binary reports the setting, and the three images start and serve under `GODEBUG=fips140=only`. The load balancer hops are FIPS-enforced in either setting.

## Container platform

Posture. The platform services and the services other teams deploy run on one ECS cluster on Fargate that the platform owns. Fargate removes host access, so no team administers an instance. Ephemeral task storage is encrypted under a customer-managed key that only Fargate tasks of this cluster can use. ECS Exec sessions are encrypted end to end under a customer-managed key and leave a transcript in an encrypted log group. A team deploys through a policy that registers only Fargate task definitions, acts only on services and tasks in this cluster, and passes only the roles the platform lists.

Controls. SC-28 protection at rest and SC-12 key management through the storage key in [ecs-cluster](../infra/terraform/ecs-cluster), whose policy binds Fargate to the cluster's encryption context and limits its grants to decryption. SC-8 and SC-13 through the KMS-encrypted Exec data channel. AU-2, AU-9, and AU-12 through the Exec transcripts in a KMS-encrypted log group. AC-3, AC-5, and AC-6 through the deployer policy, which a team cannot use outside the cluster or to pass an unlisted role. CA-7 continuous monitoring through Container Insights.

## Kubernetes cluster

Posture. The activity worker, LiteLLM, the inbound webhook, the MCP gateway, and the sandbox, gate, checks, and scanner pods run on an EKS cluster whose API endpoint is reachable only inside the VPC. Access is granted through access entries alone, so no principal holds access through the `aws-auth` ConfigMap or as the cluster creator. The sandbox pods run on a separate tainted node group. Nodes require IMDSv2 at a hop limit of 1, so a pod cannot read the node role, and each workload that calls AWS receives credentials from a Pod Identity role that only its own namespace and service account can assume. The VPC CNI enforces NetworkPolicy, in strict mode once the cluster and platform policies are applied.

Controls. SC-7 boundary protection through the private endpoint and the NetworkPolicy enforcement in [eks-cluster](../infra/terraform/eks-cluster). SC-28 and SC-12 through the customer-managed keys for the Kubernetes secrets, the node volumes, and the control plane logs. AU-2, AU-9, and AU-12 through the api, audit, and authenticator control plane logs in a KMS-encrypted log group. AC-2, AC-3, and AC-6 through the access entries and the Pod Identity roles bound to one service account each. CM-7 least functionality through the IMDSv2 hop limit.

The gate, checks, and scanner pods run repository and tool code, so they reach no public registry directly. `registry_mode` in the [private-bedrock](../infra/terraform/examples/private-bedrock) composition selects their source. In `external` mode an organization's Artifactory or compatible service is the single external connection, reached on 443 at its own ranges with a read-only token held in Secrets Manager. In `aws` mode images come through ECR pull-through caches inside the account, and the pods reach the PyPI, npm, and Go module indexes on 443, which DNS Firewall resolves by name while the NetworkPolicy admits any address outside the VPC. A pod that connects to a literal address is the residual exposure of `aws` mode, so `external` mode is the posture for an authorization boundary that must enumerate every external connection under SC-7 and CA-3.

## Tenant boundary

Posture. Teams share a deployment as tenants, and a tenant is the trust boundary that owns a set of credentials and everything that may see them. The `tenants` map of the [private-bedrock](../infra/terraform/examples/private-bedrock/README.md#tenants) composition gives each tenant its own activity worker in the `tenant-<tenant>` namespace under the Pod Identity role `<cluster>-tenant-<tenant>`, its own sandbox namespace `tenant-<tenant>-sandbox`, its own Temporal task queue, and, through the [tenant](../infra/terraform/tenant) module, its own KMS key, secrets, ECR prefix, config bundle prefix, publisher role, Signer profile, rebar ticket store, and EFS workspace access point. Each tenant secret's resource policy denies `GetSecretValue` to every principal except the tenant's worker role, the worker policy reads only the tenant's bundle prefix and image prefix, the ticket store roles trust only the tenant's worker and operators, and each worker mounts only its tenant's workspace access point, so one tenant's worker cannot read another tenant's credentials, tickets, config, or checkouts. The sandbox namespace's RoleBinding grants pod creation only to the tenant's own worker, its network policies admit traffic only from and to that worker among the tenant namespaces, and its optional ResourceQuota bounds the pods a tenant runs. A tenant changes its work only by publishing a config bundle from its own config repository through a GitHub OIDC publisher role limited to `allowed_refs`, which can write the tenant's bundle prefix and image prefix and cannot read a bundle object. Each worker validates a new bundle against the platform's image policy and the catalog before it activates it, keeps the last valid bundle active when a new one fails, and records the version of each bundle file in each run's determinism manifest. A bundle can never replace a platform file such as `image_policy.yaml` or `review-trust-root.yaml`. Every image a tenant pod runs passes the five layers of [image governance](image-governance.md), which are bundle validation, the ECR pull scope, the `agentic-dev-platform-tenant-images` ValidatingAdmissionPolicy, buildah's `policy.json`, and the Amazon Inspector scan gate with optional AWS Signer verification. Each tenant namespace also runs the tenant's own [MCP gateway](#mcp-gateway) under the worker's service account. The platform's inbound webhook verifies a pull request delivery against the secret of each tenant whose `repositories.yaml` lists the repository and routes it to the tenant whose secret verifies it, refusing a delivery that no secret verifies and refusing one that more than one tenant's secret verifies, because tenants that share a secret can forge each other's deliveries. It accepts a Jira delivery only on `/webhook/jira/<tenant>`, with that tenant's secret and project allowlist, and starts the intake on the tenant's task queue, where the tenant's worker reads Jira, so the webhook holds no Jira credentials. With two or more tenants, each tenant's webhook secrets admit only the inbound webhook role, which reads only the `tenants/<tenant>/` bundle prefixes. Repository intelligence reads the current and previous version of each tenant's token at runtime with its task role, the token rotates on a schedule, and the tenant's activity worker and MCP gateway restart after each rotation. `inv tenant-verify-aws` checks a deployed environment against this boundary. It simulates each tenant secret's policy for the named readers, the other tenants' roles, and the admin role, lists the variable and file names, never the values, in every tenant container, probes repository intelligence for 401, 403, and 200 answers, checks each tenant's mounts, and exits 1 on any failure.

Controls. AC-4 information flow enforcement through the per-tenant network policies of the sandbox namespaces, the per-tenant task queues, and the tenant workspace access points, which keep one tenant's runs, checkouts, and pods apart from another's, and through repository intelligence, which serves each tenant only the repositories of that tenant's bundle and reads each tenant's checkouts under its own `/tenants/<tenant>/repositories`, and through the inbound webhook, which routes each delivery to the one tenant that owns its repository or that its Jira path names, and through each tenant's MCP gateway, whose evidence reads join each artifact to the tenant recorded on its execution. IA-9 service identification and authentication through the per-tenant repository intelligence token, which the tenant worker presents and repository intelligence compares in constant time, answering 401 without a known token and 403 for another tenant's repository. IA-5 authenticator management through the scheduled rotation of that token, which repository intelligence accepts in its current and previous versions so a worker keeps its access until it restarts. IA-3 through each tenant's own GitHub and Jira webhook secrets, so one tenant cannot sign another tenant's deliveries. AC-6 least privilege through the per-tenant worker role and worker policy, the secret resource policies that admit only that role, the webhook secret policies that admit only the inbound webhook role, the sandbox RoleBinding, and the publisher role that may write but not read the tenant's bundle. SC-7 boundary protection through the tenant namespaces, the sandbox network policies, and the ECR pull scope that confines a tenant's pods to the catalog, its own prefix, and the pull-through caches. CM-3 configuration change control through the publisher role, the validation before activation, the keep-last-valid rule, and the bundle version recorded in the determinism manifest of each run. CM-5 access restrictions for change through the GitHub OIDC trust on the tenant's config repository and `allowed_refs`, and through the platform files a bundle may not replace. CM-7 least functionality through the admission policy, the image policy, and buildah's `policy.json`, which admit only digest-pinned images from listed repositories. SI-7 software and information integrity through the digest requirement, the Inspector scan gate, and, with `image_signature_verification`, the Signer signature check against the platform profile for catalog images and the tenant's profile for tenant images. AU-3 and AU-12 attribution through the tenant recorded on each execution, the `tenant:<tenant>` tag on each model call, the CloudTrail object-level events on the tenant config bucket and each tenant's ticket store, and the `tenant` tag on each tenant resource, which also splits the bill. CA-2 control assessment through `inv tenant-verify-aws`, which tests the secret policies, the container environments, repository intelligence, and the mounts of each tenant in the deployed environment.

## Platform services

Posture. The workflow and review workers, coordination, repository intelligence and its index worker, Langfuse web and worker, ClickHouse, and the collector run as Fargate services on the platform ECS cluster in the application tier with no public address, and the `db-migrate` and `schedule-bootstrap` one-shot tasks run in the management tier. Nothing runs in the data tier. Each workload has its own task role, execution role, security group, and KMS-encrypted log group. A task role grants only the actions its workload calls, so only the review worker holds `bedrock:InvokeModel`, only the collector writes to X-Ray and the Prometheus workspace, and only the index writers write the repository index. Each execution role reads only the secrets its task injects, and the task definitions carry secret ARNs and no secret values. Repository intelligence reads each tenant's repository intelligence token at runtime with its task role, whose only Secrets Manager grant is `GetSecretValue` on those secrets, rather than through its execution role. Repository intelligence, the index worker, and the review worker read only `tenants/*` of the tenant config bucket. Every container runs on a read-only root file system, and only a setup or init container runs as root, prepares a task volume, and exits. The images are pinned by digest in KMS-encrypted ECR repositories with immutable tags and scan on push. Every AWS SDK call goes to the service's FIPS endpoint where one exists, Bedrock included through its `bedrock-runtime-fips` interface endpoint.

Service-to-service traffic is encrypted on every hop, which is how the platform meets SC-8 inside the VPC.

| Hop | Protection |
|---|---|
| Client to the internal load balancer | TLS 1.2 or 1.3 under `ELBSecurityPolicy-TLS13-1-2-FIPS-2023-04`, with a certificate the clients verify against the platform CA |
| Internal load balancer to a task | TLS to a certificate each task issues itself at start. The load balancer does not verify it, and the task's group admits only the load balancer |
| Worker to the Temporal frontend | TLS with host verification against the Temporal CA, through the Temporal client group |
| Service to Aurora | TLS with host verification against the RDS CA bundle, `verify-full` for the Python clients and `sslaccept=strict` for Langfuse |
| Langfuse to Valkey | TLS to the ElastiCache endpoint, which requires it |
| Langfuse to ClickHouse | HTTPS and the native protocol over TLS, verified against the platform CA. ClickHouse serves no plain port, and the deploy runs the ClickHouse migrations with verification |
| Task to EFS | NFS over TLS through an access point with IAM authorization, which the file system policies require |
| Collector to X-Ray, the Prometheus workspace, and Langfuse | TLS to the `xray-fips` and `aps-workspaces` interface endpoints with SigV4, and to Langfuse through the internal load balancer with basic auth |

Controls. SC-7 boundary protection through the tier placement, the per-workload groups that admit only declared ports from declared sources, and the internal load balancer in [container-services](../infra/terraform/container-services). SC-8 and SC-8(1) through the hops above. SC-13 through the FIPS policy on the load balancer and the FIPS service endpoints. SC-12 through the platform CA, which issues the load balancer and ClickHouse certificates outside the repository, and the module's KMS keys for the logs, the workspace file system, the ClickHouse certificate secret, and the telemetry workspace. SC-28 through those keys and the encrypted file systems. AC-3, AC-4, and AC-6 through the per-workload task roles, the per-secret reader policies, the task-role read of the tenant tokens, the `tenants/*` limit on the tenant config readers, and the groups. IA-5 through the scheduled credential rotation, the restart of every service that reads a rotated credential, and the [off-hours](../infra/terraform/off-hours) schedule, which keeps the services at zero across the rotation window so no connection is refused. AU-2 and AU-12 through the task logs, the load balancer access logs, and the traces in X-Ray. CA-7 through the collector's traces and metrics. CM-2, CM-6, and CM-7 through the pinned images and the read-only root file systems.

Open items. The TLS a task terminates and the TLS its clients open run in the Python, Node, and Go runtimes of the images, which do not run a CMVP-validated module in FIPS mode, because Fargate offers FIPS mode only in AWS GovCloud. Langfuse's FIPS mode also needs a Government license. The load balancer hop and the AWS endpoints do run validated modules. Amazon Managed Service for Prometheus offers no FIPS endpoint for remote write. The load balancer does not authenticate the task certificate, so the hop to a task relies on the target group's security group for its peer. The [control inheritance matrix](fedramp-control-inheritance.md) tracks these items.

## Dashboards

Posture. An Amazon Managed Grafana workspace from [managed-grafana](../infra/terraform/managed-grafana) holds the dashboards over the collector's metrics in the Prometheus workspace and its traces in X-Ray. Users sign in only through IAM Identity Center, and Identity Center groups receive the Grafana Admin, Editor, and Viewer roles. The workspace connects to the application tier, and its group admits no ingress and egress only to the interface endpoints, so its data source traffic reaches Prometheus and X-Ray through the `aps-workspaces` and `xray` endpoints. The workspace role holds the four Prometheus query actions on the one workspace and the X-Ray read actions, no write action, and no role assumption. An optional query role holds the same four query actions for the operators the composition names, and only they may assume it. The collector role writes and the workspace and query roles read, so no role does both. A customer managed key with rotation encrypts the workspace outside AWS GovCloud (US). Plugin installation from the Grafana UI is off. The `grafana-workspace` endpoint gives operators an in-VPC path to the workspace, and network access control can admit only that endpoint. A Grafana Admin adds the two data sources from the module's output, so no Grafana credential is stored in the Terraform state.

| Hop | Protection |
|---|---|
| User to the workspace | TLS, with IAM Identity Center sign-in, and through the `grafana-workspace` endpoint when network access control admits only it |
| Workspace to Prometheus | TLS to the `aps-workspaces` interface endpoint with SigV4 under the workspace role |
| Workspace to X-Ray | TLS to the `xray` interface endpoint with SigV4 under the workspace role |

Controls. CA-7 continuous monitoring through the dashboards over the platform's metrics and traces, which the deploying organization's monitoring program consumes. AU-6 audit review, analysis, and reporting through the trace views. AC-2 and IA-2 through Identity Center sign-in and group-based roles. AC-6 through the separate write and read roles, the workspace role limited to the query actions on one workspace and trace reads, and the query role limited to the named operators. SC-7 through the VPC connection with egress only to the endpoints and the optional inbound restriction to the `grafana-workspace` endpoint. SC-8 through TLS on every hop. SC-12 and SC-28 through the workspace key. CM-7 through disabled plugin installation.

Open items. Amazon Managed Grafana accepts no customer managed key in AWS GovCloud (US), where the workspace uses an AWS owned key. Its workspace and data source calls use the standard regional endpoints rather than FIPS endpoints. Dashboard and alert rule content is the deploying organization's.

## Edge endpoints

Posture. The platform reaches AWS services through interface and gateway VPC endpoints rather than the public internet, so traffic to Bedrock, the object store, and the other consumed services stays on the AWS network. Bedrock inference is authorized by a dedicated IAM policy.

Controls. SC-7 boundary protection and AC-4 information flow enforcement through the [vpc-endpoints](../infra/terraform/vpc-endpoints) interface endpoints with private DNS and the S3 gateway endpoint. SC-8 transmission confidentiality over TLS to every endpoint. AC-6 least privilege for inference through the `bedrock:InvokeModel` policy in [bedrock-iam](../infra/terraform/bedrock-iam), attached to the role that signs Bedrock calls.

## Network zones and egress

Posture. A created network separates its zones into subnet tiers, each with its own route table. The public tier holds only the NAT path. The application tier holds the services and the interface endpoints. The management tier holds the jumphost and administrative tasks. The data tier holds the databases and the ClickHouse file system, has no route to the internet, and admits only the database, cache, and NFS ports from the application and management tiers. Outbound traffic from the application and management tiers leaves through one NAT path, and the VPC resolves only an allowlist of AWS, GitHub, Atlassian, and Slack names. Data is protected by at least three challenges on separate resources: the data-tier network ACL, the per-service security groups, and database authentication over enforced TLS.

Controls. SC-7 boundary protection through the tiered subnets, the data-tier network ACL, and the data-tier security groups without egress in the [private-bedrock](../infra/terraform/examples/private-bedrock) composition root, which separates the publicly routed tier from the internal tiers. SC-7(5) deny by default through the [dns-firewall](../infra/terraform/dns-firewall) allowlist, which answers NXDOMAIN for every other name and fails closed. SC-7(3) and SC-7(4) limited, managed access points through the single NAT path in the [egress](../infra/terraform/egress) module. AC-4 information flow enforcement through the per-tier route tables, which give the data tier no default route. AU-12 audit generation through the resolver query log. CM-6 and SI-2 for the NAT instance through Amazon Linux 2023 minimal with IMDSv2 required, no SSH, Systems Manager administration, and security updates at boot.

## Data tier

Posture. Evidence and audit objects persist to an object store under a write-once-read-many retention that a delete or an overwrite cannot bypass within the window, and the Postgres tables remain the queryable index. Objects are encrypted at rest and reachable only over TLS.

Controls. AU-9 protection of audit information through S3 Object Lock in compliance mode in the [evidence-store](../infra/terraform/evidence-store) module, which forbids early delete or overwrite including by the account root. SC-28 protection at rest through SSE-KMS or SSE-S3 encryption on the bucket. SC-8 through the TLS-only bucket policy. SI-12 information retention through the default Object Lock retention window. AC-6 through the writer-allowlist bucket policy.

Posture. The platform database runs as Aurora PostgreSQL and the Langfuse queue and cache as ElastiCache for Valkey, both in the data tier, encrypted at rest, and reachable only over TLS. The database master password is generated and rotated by RDS in Secrets Manager and never enters Terraform state. The cache refuses unauthenticated connections and admits one RBAC user. ClickHouse keeps its data on an encrypted EFS file system that admits mounts only over TLS and only through its access point. Langfuse uploads land in an encrypted, TLS-only bucket. Terraform state is held in an encrypted, versioned, TLS-only bucket rather than on a workstation. The rebar ticket store syncs to its own bucket under a dedicated KMS key, fetched under a reader role and pushed under a separate writer role, and the activity worker refuses to start when the store's configuration overlaps the evidence or audit stores.

Controls. SC-28 protection at rest through Aurora storage encryption in [aurora-postgresql](../infra/terraform/aurora-postgresql), ElastiCache at-rest encryption in [elasticache](../infra/terraform/elasticache), EFS encryption in [clickhouse-storage](../infra/terraform/clickhouse-storage), and SSE on the [langfuse-blob-store](../infra/terraform/langfuse-blob-store) and [tf-state](../infra/terraform/tf-state) buckets. SC-8 transmission confidentiality through `rds.force_ssl`, ElastiCache transit encryption set to `required`, the EFS file system policy, and the TLS-only bucket policies. IA-5 authenticator management through the RDS-managed rotating master secret and the ElastiCache credential stored in Secrets Manager in the rotation format. AC-3 and AC-6 through IAM database authentication, the RBAC access string, the disabled default cache user, and the EFS access point. AU-2 and AU-12 through pgaudit DDL logging, connection logging, and the exported PostgreSQL and Valkey engine logs. CP-9 system backup through 30-day Aurora automated backups, ElastiCache snapshots, EFS automatic backups through AWS Backup, and versioned buckets. CP-10 recovery through Aurora storage replicated across three Availability Zones, with instance and node counts raised for production failover. SC-13, SC-28, SC-8, and AC-6 for the ticket store through SSE-KMS with an S3 Bucket Key, a bucket policy that requires TLS 1.2 and allows object access only to the store roles, and the startup isolation check in [rebar-ticket-store](../infra/terraform/rebar-ticket-store). AU-2 and AU-12 for the ticket store through CloudTrail data events on every object read and write, denied requests included.

## Secrets

Posture. Secret material reaches a workload from AWS Secrets Manager rather than from source. The [secret-store](../infra/terraform/secret-store) module encrypts every secret with a dedicated KMS key, allows each secret to be read only by the roles that consume it, and injects the values into tasks at start. Each service connects to PostgreSQL as its own role, limited to its own database, rather than as the master user. The database and cache credentials rotate on a quarterly schedule in an after-hours window, the consuming services redeploy when a credential changes, and the README runbook covers the event-driven rotation of every other secret. Each tenant's repository intelligence token rotates every 30 days by default through a token rotation function whose role reaches only the secrets that match the tenant token name pattern and uses their keys only under the `kms:EncryptionContext:SecretARN` condition, and the tenant's activity worker and MCP gateway restart after each rotation. The trust-root bundle, which holds only public keys, ships as non-secret configuration.

Controls. IA-5 authenticator management through the organization-defined rotation period and event triggers of IA-5(f) and IA-5(i), the scheduled rotation of each tenant's repository intelligence token, generated values that never enter Terraform state, and passwords set as SCRAM verifiers so no log holds them. IA-5(7) through secrets that live only in Secrets Manager and never in source or images. AC-6 least privilege through the per-secret resource policies, the per-service database roles, and the token rotation role limited to the tenant token secrets. SC-12 cryptographic key establishment through the KMS keys the modules consume, with automatic key rotation enabled on the secret-store key and the key in [bedrock-jumphost-fargate](../infra/terraform/bedrock-jumphost-fargate), and through the encryption context condition that confines the token rotation role to the keys of the secrets it rotates. SC-28 at-rest protection of secret values under the customer managed key.

## Identity

Posture. Each workload assumes a scoped role rather than sharing a static credential, and each authoring agent signs the plan and the code change it produces under its own rebar identity. The merge gate verifies both signatures against the identity trust root and fails closed on an absent or out-of-trust-root signature.

Controls. IA-2 and IA-5 identification and authenticator management through per-identity keyrings with trust-on-first-use genesis, signed rotation, and revocation, described in [authored-identity-signing.md](authored-identity-signing.md). AU-10 non-repudiation through the authorship signatures bound to the produced artifact. AC-6 least privilege through the scoped IAM roles in [bedrock-iam](../infra/terraform/bedrock-iam) and [bedrock-jumphost-fargate](../infra/terraform/bedrock-jumphost-fargate).

## Images

Posture. Container images are built from pinned bases and pushed to a registry that scans on push and forbids tag reuse, so a deployed image has a known provenance and a vulnerability record. The publish scans each platform image with Amazon Inspector before the push, signs the catalog images with the platform's AWS Signer profile, and attaches a build provenance attestation to each image it pushes. A tenant pod runs an image only after the layers the [tenant boundary](#tenant-boundary) lists.

Controls. CM-2 and CM-6 baseline configuration through immutable tags and the lifecycle policy in the [ecr](../infra/terraform/ecr) module. RA-5 vulnerability scanning through scan-on-push in the same module and through the `inv sast` CI gate, which runs SAST, secret, infrastructure misconfiguration, and dependency scans and fails on any finding the [accepted-findings register](../security/sast-accepted.yaml) does not justify. SA-11 developer testing through the same gate on every pull request. SI-7 software and information integrity through the pinned base image and the immutable tag. SR-3 and SR-4 supply chain controls through the managed registry, the pinned provenance, and the build provenance attestations. RA-5 also through the Inspector scan before each platform image push and the scan gate before each tenant pod pull, which accept a finding only through a reviewed entry of `platform/image_exceptions.yaml` or, for the tenant's own images, the tenant's bundle `image_exceptions.yaml`. SI-7 also through the Signer signatures on the catalog and tenant images.

## Audit export

Posture. Platform decisions write to an append-only audit trail, control-plane API activity writes to CloudTrail, and both the evidence objects and the audit objects persist to the object store under Object Lock. The trail carries log-file integrity validation.

Controls. AU-2 and AU-12 audit generation through the platform `audit_events` records and CloudTrail. AU-3 content of audit records through the committed [audit-event schema](../schemas/audit_events/audit-event.schema.json), and through the tenant recorded on each execution and carried as the `tenant:<tenant>` tag of each LiteLLM request and Langfuse trace and as the `tenant` attribute of each span, which attributes every model call and its cost to the tenant of its run. AU-9 protection of audit information through CloudTrail log-file validation and Object Lock on the evidence and audit objects, and the TLS-only trail bucket and the customer-managed key that encrypts the trail log files in the [cloudtrail](../infra/terraform/cloudtrail) module. AU-2 and AU-12 object-access records through S3 server access logging from every platform bucket to the bucket in the [access-logs](../infra/terraform/access-logs) module. AU-11 audit record retention through the Object Lock retention window, and for access logs through 12 months in S3 Standard followed by 18 months in Glacier Instant Retrieval.

## MCP gateway

Posture. Each tenant runs its own MCP gateway in its `tenant-<tenant>` namespace under the tenant worker's service account. The gateway serves eight read tools that return Jira tickets, private repository content, security findings, and evidence records under the tenant's credentials, Jira project allowlist, repository allowlist, and repository intelligence token. Its evidence and security-finding reads return only the executions recorded for the tenant, so another tenant's identifiers read as not found. It sits behind the tenant's own internal load balancer, which admits only the subnets of the gateway's clients, and its network policy admits ingress from the VPC on port 8150 only. Every request to its MCP endpoint must present the tenant's bearer token, which the [tenant](../infra/terraform/tenant) module generates in Secrets Manager under the tenant key and only the tenant's worker role reads. The gateway compares the token in constant time and refuses a request without it before any tool runs. Only the health paths, which return a fixed status body, answer without the token. The gateway refuses to start without a token or without `TENANT`, so a misconfiguration cannot leave the tools open or unscoped.

Controls. AC-3 access enforcement through the token check that gates every tool listing and invocation in [auth.py](../services/integration/mcp_gateway/auth.py). AC-4 information flow enforcement through the tenant filter on every evidence and security-finding read in [evidence_reader.py](../services/integration/mcp_gateway/evidence_reader.py). AC-6 least privilege through the gateway's run under the tenant worker's identity, which reads only the tenant's secrets. IA-2 identification and authentication through the per-tenant bearer token, generated and held in [mcp_gateway.tf](../infra/terraform/tenant/mcp_gateway.tf) of the tenant module and mounted at start, so the gateway serves no unauthenticated client. SC-7 boundary protection through the internal load balancer scheme and the `inbound-cidrs` annotation in [mcp-gateway.yaml](../deploy/kubernetes/mcp-gateway.yaml), which limits each tenant load balancer's security group to the client subnets each environment declares, and through the tenant gateway's copies of the platform network and security group policies.

Open items. One token is shared by every client of a tenant's gateway, so the gateway authenticates the tenant's client population rather than an individual client, and a token change is a coordinated rotation across those clients. The tools read with the tenant's credentials rather than the caller's.

## Webhook relay policy

Posture. The single public ingress is the webhook receiver. It authenticates each inbound delivery, rejects an unsigned or mis-signed request, and converges duplicate deliveries on one outcome through the coordination idempotency ledger. An integration configured for inbound deliveries refuses to start without its signing secret, so an unconfigured secret cannot degrade into accepting unsigned traffic. Every request handler that reads a body bounds the declared length, and every request handler sets a connection timeout, so a client that declares a body and sends nothing releases its handler thread rather than holding it.

Controls. SI-10 information input validation through the HMAC-SHA256 signature check with a constant-time comparison in [pr_events.py](../services/orchestration/webhook/pr_events.py). IA-3 device and sender authentication through the webhook secret of the tenant that owns each delivery, held in [tenants.py](../services/orchestration/webhook/tenants.py), and on the coordination RPC through the shared bearer token checked in [service.py](../services/coordination/service.py). AC-4 information flow enforcement through the routing of each pull request delivery to the one tenant that lists its repository and of each Jira delivery to the tenant its `/webhook/jira/<tenant>` path names, admitted only for that tenant's allowlisted projects and handed to that tenant's task queue. SC-8 transmission confidentiality over TLS. SC-5 denial-of-service consideration through the idempotency ledger that collapses duplicate deliveries, and through the body cap and connection timeout in [http_front_door.py](../services/http_front_door.py).

## Cross-cutting integrity

Posture. Every review verdict is signed with an asymmetric SSHSIG signature carried in a DSSE envelope and verified against a public trust root before the gate accepts it, so a verifier holding only public keys cannot forge a verdict.

Controls. SI-7 software and information integrity and AU-10 non-repudiation through the signed verdicts described in [review-verdict-signing.md](review-verdict-signing.md). SC-12 and SC-13 cryptographic key management and cryptographic protection through the trust-root bundle with per-key validity windows, revocation, and an overlapping rotation window.

# FedRAMP Medium hardening design

This design ties each platform component to the FedRAMP Medium control families it satisfies, grounded in the controls the platform implements today. It is a design reference. It provisions nothing and changes no runtime code. The platform-owned controls that are not yet met are tracked as dedicated v0.3.0 features in the [roadmap](../ROADMAP.md), not in this document.

Control family labels follow NIST SP 800-53 Revision 5. A mapping to a family cites the terraform module or the code that implements the control, so the posture is verifiable rather than aspirational. The companion [local-to-AWS mapping](local-to-aws-mapping.md) records where each component runs in a deployed environment.

## Trust boundary and deployment posture

The platform runs inside the target VPC. It reaches the private `bedrock-runtime` interface endpoint with the direct connectivity provider and no hop, and it has no public ingress except the webhook receiver, which authenticates every request. Private reachability comes from the shared interface and gateway endpoints in the [vpc-endpoints](../infra/terraform/vpc-endpoints) module, whose security group admits port 443 only from in-VPC subnets. This establishes the boundary the SC family protects.

## Control inheritance

The platform is hosted on an AWS account that holds a FedRAMP Medium authorization. Under the FedRAMP shared-responsibility model the platform inherits the controls AWS owns and implements the controls it configures on top. The physical and environmental families, the hypervisor and host controls, the FIPS-validated cryptographic modules behind KMS and the FIPS service endpoints, the durability and availability of the managed services, and the underlying network fabric are inherited from the AWS authorization. The platform is responsible for how it configures and uses those services, which is encryption enabled, least-privilege IAM, audit logging turned on, retention set, network isolation applied, FIPS endpoints selected, and secrets managed. The control inheritance and shared-responsibility matrix in [fedramp-control-inheritance.md](fedramp-control-inheritance.md) records the per-family split of inherited, platform-implemented, and deploying-organization controls. The sections below describe the platform-implemented portion. The platform-owned controls that are not yet met are tracked as v0.3.0 features in the [roadmap](../ROADMAP.md).

## Temporal control plane

Posture. The Temporal server runs as a Fargate service on the platform ECS cluster in the application tier, with no public address. Clients reach the frontend through an internal NLB that admits port 7233 only from the Temporal client security group, and the server tasks admit the frontend only from the NLB and the internode ports only from each other. The frontend serves TLS, and the internode listeners require mutual TLS with a certificate from the configured CA and refuse any other peer. The frontend certificate comes from a CA the platform generates, from the deploying organization's PKI, or from ACM. When it comes from ACM, the NLB terminates the client connection under the `ELBSecurityPolicy-TLS13-1-2-FIPS-2023-04` policy, which negotiates TLS 1.2 and 1.3 only, and re-encrypts to the server. The certificates and keys live in Secrets Manager under a dedicated KMS key, never pass through Terraform, and are readable only by the execution roles of the tasks that use them. Only the server reads a private key. The server and the admin-tools task connect to Aurora over TLS with host verification against the RDS CA bundle, whose SHA-256 the image build pins, using the `temporal` role from the secret store, and a rotation of that password redeploys the server. The admin-tools task applies the schemas before any server of a new version starts. The UI runs in the management tier behind an internal HTTPS ALB under the same FIPS policy, which admits only the jumphost task group and the listed operator networks, and it connects to the frontend over TLS with host verification. Every container runs as a non-root user on a read-only root file system, except an init container that runs as root to make the scratch volume writable and then exits. The task definitions hold secret ARNs and no secret values. The images are built from upstream images pinned by digest and pushed to KMS-encrypted ECR repositories with immutable tags and scan on push. Task logs go to CloudWatch log groups under the module's KMS key, and both load balancers write access logs to a TLS-only bucket. ECS Exec into the Temporal tasks is off unless enabled.

Controls. SC-7 boundary protection through the internal load balancers, the client and server security groups, and the tier placement in [temporal-control-plane](../infra/terraform/temporal-control-plane). SC-8 and SC-8(1) through TLS on the frontend and the UI, mutual TLS between the server tasks, and TLS with host verification to Aurora. SC-13 through the FIPS security policies on both load balancers and, with `fips_140_mode` enabled, Go's FIPS 140-3 mode in the server, admin-tools, and UI processes, which refuses non-approved algorithms such as ChaCha20-Poly1305 and X25519 on the frontend and internode listeners. SC-12 through the dedicated KMS key for the TLS secrets and the ACM expiry events routed to an SNS topic. SC-28 through KMS encryption of the secrets, the log groups, and the image repositories. IA-5(2) public key-based authentication through the internode certificate check. AC-3, AC-4, and AC-6 through the client security group, the per-secret reader policies, and the per-task execution roles. AU-2, AU-11, and AU-12 through the task logs and the load balancer access logs with their retention. CM-2, CM-6, and CM-7 through the pinned images, the managed dynamic configuration that refuses the removed Worker Versioning V1 keys, and the read-only root file systems. RA-5 through scan on push.

Open item. `fips_140_mode` sets `GODEBUG=fips140=on`, which enforces FIPS-approved algorithms through the Go Cryptographic Module built into the upstream binaries. Those binaries are compiled without a `GOFIPS140` setting, so the module is the in-tree one rather than a CMVP-validated snapshot. The TLS the server terminates in secrets mode, the internode mutual TLS, and the UI connection to the frontend therefore do not yet run on a validated module. The load balancer hops do. The [control inheritance matrix](fedramp-control-inheritance.md) tracks this item.

## Container platform

Posture. The platform services and the services other teams deploy run on one ECS cluster on Fargate that the platform owns. Fargate removes host access, so no team administers an instance. Ephemeral task storage is encrypted under a customer-managed key that only Fargate tasks of this cluster can use. ECS Exec sessions are encrypted end to end under a customer-managed key and leave a transcript in an encrypted log group. A team deploys through a policy that registers only Fargate task definitions, acts only on services and tasks in this cluster, and passes only the roles the platform lists.

Controls. SC-28 protection at rest and SC-12 key management through the storage key in [ecs-cluster](../infra/terraform/ecs-cluster), whose policy binds Fargate to the cluster's encryption context and limits its grants to decryption. SC-8 and SC-13 through the KMS-encrypted Exec data channel. AU-2, AU-9, and AU-12 through the Exec transcripts in a KMS-encrypted log group. AC-3, AC-5, and AC-6 through the deployer policy, which a team cannot use outside the cluster or to pass an unlisted role. CA-7 continuous monitoring through Container Insights.

## Kubernetes cluster

Posture. The activity worker, LiteLLM, the inbound webhook, the MCP gateway, and the sandbox, gate, checks, and scanner pods run on an EKS cluster whose API endpoint is reachable only inside the VPC. Access is granted through access entries alone, so no principal holds access through the `aws-auth` ConfigMap or as the cluster creator. The sandbox pods run on a separate tainted node group. Nodes require IMDSv2 at a hop limit of 1, so a pod cannot read the node role, and each workload that calls AWS receives credentials from a Pod Identity role that only its own namespace and service account can assume. The VPC CNI enforces NetworkPolicy, in strict mode once the cluster and platform policies are applied.

Controls. SC-7 boundary protection through the private endpoint and the NetworkPolicy enforcement in [eks-cluster](../infra/terraform/eks-cluster). SC-28 and SC-12 through the customer-managed keys for the Kubernetes secrets, the node volumes, and the control plane logs. AU-2, AU-9, and AU-12 through the api, audit, and authenticator control plane logs in a KMS-encrypted log group. AC-2, AC-3, and AC-6 through the access entries and the Pod Identity roles bound to one service account each. CM-7 least functionality through the IMDSv2 hop limit.

The gate, checks, and scanner pods run repository and tool code, so they reach no public registry directly. `registry_mode` in the [private-bedrock](../infra/terraform/examples/private-bedrock) composition selects their source. In `external` mode an organization's Artifactory or compatible service is the single external connection, reached on 443 at its own ranges with a read-only token held in Secrets Manager. In `aws` mode images come through ECR pull-through caches inside the account, and the pods reach the PyPI, npm, and Go module indexes on 443, which DNS Firewall resolves by name while the NetworkPolicy admits any address outside the VPC. A pod that connects to a literal address is the residual exposure of `aws` mode, so `external` mode is the posture for an authorization boundary that must enumerate every external connection under SC-7 and CA-3.

## Platform services

Posture. The workflow and review workers, coordination, repository intelligence and its index worker, Langfuse web and worker, ClickHouse, and the collector run as Fargate services on the platform ECS cluster in the application tier with no public address, and the `db-migrate` and `schedule-bootstrap` one-shot tasks run in the management tier. Nothing runs in the data tier. Each workload has its own task role, execution role, security group, and KMS-encrypted log group. A task role grants only the actions its workload calls, so only the review worker holds `bedrock:InvokeModel`, only the collector writes to X-Ray and the Prometheus workspace, and only the index writers write the repository index. Each execution role reads only the secrets its task injects, and the task definitions carry secret ARNs and no secret values. Every container runs on a read-only root file system, and only a setup or init container runs as root, prepares a task volume, and exits. The images are pinned by digest in KMS-encrypted ECR repositories with immutable tags and scan on push. Every AWS SDK call goes to the service's FIPS endpoint where one exists, Bedrock included through its `bedrock-runtime-fips` interface endpoint.

Service-to-service traffic is encrypted on every hop, which is how the platform meets SC-8 inside the VPC.

| Hop | Protection |
|---|---|
| Client to the internal load balancer | TLS 1.2 or 1.3 under `ELBSecurityPolicy-TLS13-1-2-FIPS-2023-04`, with a certificate the clients verify against the platform CA |
| Internal load balancer to a task | TLS to a certificate each task issues itself at start. The load balancer does not verify it, and the task's group admits only the load balancer |
| Worker to the Temporal frontend | TLS with host verification against the Temporal CA, through the Temporal client group |
| Service to Aurora | TLS with host verification against the RDS CA bundle, `verify-full` for the Python clients and `sslaccept=strict` for Langfuse |
| Langfuse to Valkey | TLS to the ElastiCache endpoint, which requires it |
| Langfuse to ClickHouse | HTTPS and the native protocol over TLS, verified against the platform CA. ClickHouse serves no plain port, and the deploy runs the ClickHouse migrations with verification |
| Task to EFS | NFS over TLS through an access point with IAM authorization, which the file system policies require |
| Collector to X-Ray, the Prometheus workspace, and Langfuse | TLS to the `xray-fips` and `aps-workspaces` interface endpoints with SigV4, and to Langfuse through the internal load balancer with basic auth |

Controls. SC-7 boundary protection through the tier placement, the per-workload groups that admit only declared ports from declared sources, and the internal load balancer in [container-services](../infra/terraform/container-services). SC-8 and SC-8(1) through the hops above. SC-13 through the FIPS policy on the load balancer and the FIPS service endpoints. SC-12 through the platform CA, which issues the load balancer and ClickHouse certificates outside the repository, and the module's KMS keys for the logs, the workspace file system, the ClickHouse certificate secret, and the telemetry workspace. SC-28 through those keys and the encrypted file systems. AC-3, AC-4, and AC-6 through the per-workload task roles, the per-secret reader policies, and the groups. IA-5 through the scheduled credential rotation, the restart of every service that reads a rotated credential, and the [off-hours](../infra/terraform/off-hours) schedule, which keeps the services at zero across the rotation window so no connection is refused. AU-2 and AU-12 through the task logs, the load balancer access logs, and the traces in X-Ray. CA-7 through the collector's traces and metrics. CM-2, CM-6, and CM-7 through the pinned images and the read-only root file systems.

Open items. The TLS a task terminates and the TLS its clients open run in the Python, Node, and Go runtimes of the images, which do not run a CMVP-validated module in FIPS mode, because Fargate offers FIPS mode only in AWS GovCloud. Langfuse's FIPS mode also needs a Government license. The load balancer hop and the AWS endpoints do run validated modules. Amazon Managed Service for Prometheus offers no FIPS endpoint for remote write. The load balancer does not authenticate the task certificate, so the hop to a task relies on the target group's security group for its peer. The [control inheritance matrix](fedramp-control-inheritance.md) tracks these items.

## Edge endpoints

Posture. The platform reaches AWS services through interface and gateway VPC endpoints rather than the public internet, so traffic to Bedrock, the object store, and the other consumed services stays on the AWS network. Bedrock inference is authorized by a dedicated IAM policy.

Controls. SC-7 boundary protection and AC-4 information flow enforcement through the [vpc-endpoints](../infra/terraform/vpc-endpoints) interface endpoints with private DNS and the S3 gateway endpoint. SC-8 transmission confidentiality over TLS to every endpoint. AC-6 least privilege for inference through the `bedrock:InvokeModel` policy in [bedrock-iam](../infra/terraform/bedrock-iam), attached to the role that signs Bedrock calls.

## Network zones and egress

Posture. A created network separates its zones into subnet tiers, each with its own route table. The public tier holds only the NAT path. The application tier holds the services and the interface endpoints. The management tier holds the jumphost and administrative tasks. The data tier holds the databases and the ClickHouse file system, has no route to the internet, and admits only the database, cache, and NFS ports from the application and management tiers. Outbound traffic from the application and management tiers leaves through one NAT path, and the VPC resolves only an allowlist of AWS, GitHub, Atlassian, and Slack names. Data is protected by at least three challenges on separate resources: the data-tier network ACL, the per-service security groups, and database authentication over enforced TLS.

Controls. SC-7 boundary protection through the tiered subnets, the data-tier network ACL, and the data-tier security groups without egress in the [private-bedrock](../infra/terraform/examples/private-bedrock) composition root, which separates the publicly routed tier from the internal tiers. SC-7(5) deny by default through the [dns-firewall](../infra/terraform/dns-firewall) allowlist, which answers NXDOMAIN for every other name and fails closed. SC-7(3) and SC-7(4) limited, managed access points through the single NAT path in the [egress](../infra/terraform/egress) module. AC-4 information flow enforcement through the per-tier route tables, which give the data tier no default route. AU-12 audit generation through the resolver query log. CM-6 and SI-2 for the NAT instance through Amazon Linux 2023 minimal with IMDSv2 required, no SSH, Systems Manager administration, and security updates at boot.

## Data tier

Posture. Evidence and audit objects persist to an object store under a write-once-read-many retention that a delete or an overwrite cannot bypass within the window, and the Postgres tables remain the queryable index. Objects are encrypted at rest and reachable only over TLS.

Controls. AU-9 protection of audit information through S3 Object Lock in compliance mode in the [evidence-store](../infra/terraform/evidence-store) module, which forbids early delete or overwrite including by the account root. SC-28 protection at rest through SSE-KMS or SSE-S3 encryption on the bucket. SC-8 through the TLS-only bucket policy. SI-12 information retention through the default Object Lock retention window. AC-6 through the writer-allowlist bucket policy.

Posture. The platform database runs as Aurora PostgreSQL and the Langfuse queue and cache as ElastiCache for Valkey, both in the data tier, encrypted at rest, and reachable only over TLS. The database master password is generated and rotated by RDS in Secrets Manager and never enters Terraform state. The cache refuses unauthenticated connections and admits one RBAC user. ClickHouse keeps its data on an encrypted EFS file system that admits mounts only over TLS and only through its access point. Langfuse uploads land in an encrypted, TLS-only bucket. Terraform state is held in an encrypted, versioned, TLS-only bucket rather than on a workstation. The rebar ticket store syncs to its own bucket under a dedicated KMS key, fetched under a reader role and pushed under a separate writer role, and the activity worker refuses to start when the store's configuration overlaps the evidence or audit stores.

Controls. SC-28 protection at rest through Aurora storage encryption in [aurora-postgresql](../infra/terraform/aurora-postgresql), ElastiCache at-rest encryption in [elasticache](../infra/terraform/elasticache), EFS encryption in [clickhouse-storage](../infra/terraform/clickhouse-storage), and SSE on the [langfuse-blob-store](../infra/terraform/langfuse-blob-store) and [tf-state](../infra/terraform/tf-state) buckets. SC-8 transmission confidentiality through `rds.force_ssl`, ElastiCache transit encryption set to `required`, the EFS file system policy, and the TLS-only bucket policies. IA-5 authenticator management through the RDS-managed rotating master secret and the ElastiCache credential stored in Secrets Manager in the rotation format. AC-3 and AC-6 through IAM database authentication, the RBAC access string, the disabled default cache user, and the EFS access point. AU-2 and AU-12 through pgaudit DDL logging, connection logging, and the exported PostgreSQL and Valkey engine logs. CP-9 system backup through 30-day Aurora automated backups, ElastiCache snapshots, EFS automatic backups through AWS Backup, and versioned buckets. CP-10 recovery through Aurora storage replicated across three Availability Zones, with instance and node counts raised for production failover. SC-13, SC-28, SC-8, and AC-6 for the ticket store through SSE-KMS with an S3 Bucket Key, a bucket policy that requires TLS 1.2 and allows object access only to the store roles, and the startup isolation check in [rebar-ticket-store](../infra/terraform/rebar-ticket-store). AU-2 and AU-12 for the ticket store through CloudTrail data events on every object read and write, denied requests included.

## Secrets

Posture. Secret material reaches a workload from AWS Secrets Manager rather than from source. The [secret-store](../infra/terraform/secret-store) module encrypts every secret with a dedicated KMS key, allows each secret to be read only by the roles that consume it, and injects the values into tasks at start. Each service connects to PostgreSQL as its own role, limited to its own database, rather than as the master user. The database and cache credentials rotate on a quarterly schedule in an after-hours window, the consuming services redeploy when a credential changes, and the README runbook covers the event-driven rotation of every other secret. The trust-root bundle, which holds only public keys, ships as non-secret configuration.

Controls. IA-5 authenticator management through the organization-defined rotation period and event triggers of IA-5(f) and IA-5(i), generated values that never enter Terraform state, and passwords set as SCRAM verifiers so no log holds them. IA-5(7) through secrets that live only in Secrets Manager and never in source or images. AC-6 least privilege through the per-secret resource policies and the per-service database roles. SC-12 cryptographic key establishment through the KMS keys the modules consume, with automatic key rotation enabled on the secret-store key and the key in [bedrock-jumphost-fargate](../infra/terraform/bedrock-jumphost-fargate). SC-28 at-rest protection of secret values under the customer managed key.

## Identity

Posture. Each workload assumes a scoped role rather than sharing a static credential, and each authoring agent signs the plan and the code change it produces under its own rebar identity. The merge gate verifies both signatures against the identity trust root and fails closed on an absent or out-of-trust-root signature.

Controls. IA-2 and IA-5 identification and authenticator management through per-identity keyrings with trust-on-first-use genesis, signed rotation, and revocation, described in [authored-identity-signing.md](authored-identity-signing.md). AU-10 non-repudiation through the authorship signatures bound to the produced artifact. AC-6 least privilege through the scoped IAM roles in [bedrock-iam](../infra/terraform/bedrock-iam) and [bedrock-jumphost-fargate](../infra/terraform/bedrock-jumphost-fargate).

## Images

Posture. Container images are built from pinned bases and pushed to a registry that scans on push and forbids tag reuse, so a deployed image has a known provenance and a vulnerability record.

Controls. CM-2 and CM-6 baseline configuration through immutable tags and the lifecycle policy in the [ecr](../infra/terraform/ecr) module. RA-5 vulnerability scanning through scan-on-push in the same module and through the `inv sast` CI gate, which runs SAST, secret, infrastructure misconfiguration, and dependency scans and fails on any finding the [accepted-findings register](../security/sast-accepted.yaml) does not justify. SA-11 developer testing through the same gate on every pull request. SI-7 software and information integrity through the pinned base image and the immutable tag. SR-3 and SR-4 supply chain controls through the managed registry and the pinned provenance.

## Audit export

Posture. Platform decisions write to an append-only audit trail, control-plane API activity writes to CloudTrail, and both the evidence objects and the audit objects persist to the object store under Object Lock. The trail carries log-file integrity validation.

Controls. AU-2 and AU-12 audit generation through the platform `audit_events` records and CloudTrail. AU-3 content of audit records through the committed [audit-event schema](../schemas/audit_events/audit-event.schema.json). AU-9 protection of audit information through CloudTrail log-file validation and Object Lock on the evidence and audit objects, and the TLS-only trail bucket and the customer-managed key that encrypts the trail log files in the [cloudtrail](../infra/terraform/cloudtrail) module. AU-2 and AU-12 object-access records through S3 server access logging from every platform bucket to the bucket in the [access-logs](../infra/terraform/access-logs) module. AU-11 audit record retention through the Object Lock retention window, and for access logs through 12 months in S3 Standard followed by 18 months in Glacier Instant Retrieval.

## MCP gateway

Posture. The MCP gateway serves eight read tools that return Jira tickets, private repository content, security findings, and evidence records under the platform's credentials. It sits behind an internal load balancer that admits only the subnets of the gateway's clients, and every request to its MCP endpoint must present a bearer token issued from Secrets Manager. The gateway compares the token in constant time and refuses a request without it before any tool runs. Only the health paths, which return a fixed status body, answer without the token. The gateway refuses to start without a token, so a misconfiguration cannot leave the tools open.

Controls. AC-3 access enforcement through the token check that gates every tool listing and invocation in [auth.py](../services/integration/mcp_gateway/auth.py). IA-2 identification and authentication through the bearer token, generated and held in the [secret-store](../infra/terraform/secret-store) module and injected at start, so the gateway serves no unauthenticated client. SC-7 boundary protection through the internal load balancer scheme and the `inbound-cidrs` annotation in [mcp-gateway.yaml](../deploy/kubernetes/mcp-gateway.yaml), which limits the load balancer's security group to the client subnets each environment declares.

Open items. One token is shared by every client, so the gateway authenticates the client population rather than an individual client, and a token change is a coordinated rotation across the clients. The tools themselves read with the platform's credentials rather than the caller's.

## Webhook relay policy

Posture. The single public ingress is the webhook receiver. It authenticates each inbound delivery, rejects an unsigned or mis-signed request, and converges duplicate deliveries on one outcome through the coordination idempotency ledger. An integration configured for inbound deliveries refuses to start without its signing secret, so an unconfigured secret cannot degrade into accepting unsigned traffic. Every request handler that reads a body bounds the declared length, and every request handler sets a connection timeout, so a client that declares a body and sends nothing releases its handler thread rather than holding it.

Controls. SI-10 information input validation through the HMAC-SHA256 signature check with a constant-time comparison in [pr_events.py](../services/orchestration/webhook/pr_events.py). IA-3 device and sender authentication through the shared webhook secret, and on the coordination RPC through the shared bearer token checked in [service.py](../services/coordination/service.py). SC-8 transmission confidentiality over TLS. SC-5 denial-of-service consideration through the idempotency ledger that collapses duplicate deliveries, and through the body cap and connection timeout in [http_front_door.py](../services/http_front_door.py).

## Cross-cutting integrity

Posture. Every review verdict is signed with an asymmetric SSHSIG signature carried in a DSSE envelope and verified against a public trust root before the gate accepts it, so a verifier holding only public keys cannot forge a verdict.

Controls. SI-7 software and information integrity and AU-10 non-repudiation through the signed verdicts described in [review-verdict-signing.md](review-verdict-signing.md). SC-12 and SC-13 cryptographic key management and cryptographic protection through the trust-root bundle with per-key validity windows, revocation, and an overlapping rotation window.

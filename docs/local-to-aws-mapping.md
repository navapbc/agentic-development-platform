# Local-to-AWS mapping

This document maps each local platform component to the AWS resource that hosts it in a deployed environment, and links the Terraform module that provisions that target where one exists. It is a mapping reference. It provisions nothing and changes no runtime code.

The authoritative per-target detail lives in each Terraform module's own README under [infra/terraform](../infra/terraform). This document consolidates and links those modules rather than restating them.

## Deployment posture

In a deployed environment the platform runs inside the target VPC. It reaches the private `bedrock-runtime` interface endpoint with `BEDROCK_CONNECTIVITY_PROVIDER=direct` and no hop. The Fargate jump-host is a laptop path for a test or development account, not a deployed component. A reader mapping the deployed system should treat the jump-host as absent and the connectivity provider as `direct`.

Workloads sign Bedrock inference with a role that carries the `bedrock:InvokeModel` policy from the [bedrock-iam](../infra/terraform/bedrock-iam) module, and private reachability comes from the shared endpoints in the [vpc-endpoints](../infra/terraform/vpc-endpoints) module.

## Component mapping

Locally the activity worker, the review worker, LiteLLM, OPA, the inbound webhook, and the MCP gateway run on the local Kubernetes cluster from the manifests in [deploy/kubernetes](../deploy/kubernetes), and the other components run in Compose. No local pod mounts a workstation directory, so the inputs each workload reads are the ones it reads in AWS, delivered as images, ConfigMaps, Secrets, and one workspace per tenant, a hostPath PersistentVolume on the cluster node that stands in for the tenant's EFS access point.

## Tenants

A tenant is the trust boundary that owns a set of credentials and everything that may see them. Each tenant has the same items locally and in AWS, with the sources below. The [README](../README.md#tenants) defines the per-tenant names, and [onboarding a tenant](../infra/terraform/examples/private-bedrock/README.md#onboarding-a-tenant) is the AWS procedure.

| Concern | Local | AWS |
|---|---|---|
| Tenant list | `TENANTS` in `.env`, or `TENANT` alone when `TENANTS` is empty | The `tenants` map of [private-bedrock](../infra/terraform/examples/private-bedrock#tenants), which sets `TENANTS` on the platform tasks and `TENANT` on each tenant's worker |
| Worker identity | The AWS credentials `inv aws-login` copies into the cluster | The Pod Identity role `<cluster>-tenant-<tenant>` with the [tenant](../infra/terraform/tenant) module's worker policy |
| Namespaces and task queue | `tenant-<tenant>`, `tenant-<tenant>-sandbox`, and `agent-platform-<tenant>` | The same names on the EKS cluster |
| Config bundle | The directory `config/local/tenants/<tenant>/`, with `TENANT_CONFIG_BUCKET` empty. A file's version is a content hash | `tenants/<tenant>/` of the [tenant-config-store](../infra/terraform/tenant-config-store) bucket, which `TENANT_CONFIG_BUCKET` names, written by the tenant's publisher role from its config repository through GitHub OIDC. A file's version is its S3 version ID |
| Secrets | `.env` for the home tenant and `config/local/tenants/<tenant>.env` for every other tenant | Secrets Manager under `<name_prefix>/tenants/<tenant>/`, encrypted with the tenant's key and readable only by the tenant's worker role. The repository intelligence token is also readable by the repository intelligence task role and its rotation function, and the webhook secrets only by the inbound webhook role |
| Images | The local registry under `host.docker.internal:5001/tenants/<tenant>/` | ECR under `<name_prefix>/tenants/<tenant>/`, with repositories created on the first push from the tenant's CI |
| Image policy | `config/local/image_policy.yaml`, copied from the example, with `scan.gate: off` and `signatures.verification: false` | Generated by the composition root, with the Amazon Inspector scan gate under `image_scanning_enabled` and AWS Signer verification under `image_signature_verification`. See [image governance](image-governance.md) |
| Workspace | A hostPath PersistentVolume at `/var/lib/agentic-dev-platform/tenants/<tenant>` on the node | An access point rooted at `/tenants/<tenant>` on the workspace EFS file system. The worker mounts either at `/tenants/<tenant>` |
| Sandbox quota | None | A ResourceQuota on the sandbox namespace from the tenant's `sandbox_quota` |
| Rebar ticket store | The `rebar-tickets` bucket in MinIO | The bucket `<tenant>-rebar-tickets-<suffix>` with the tenant's reader and writer roles |
| LiteLLM team | Created by the worker in the `litellm` database of the Compose `postgres` | Created by the worker in the `litellm` database on Aurora |
| Repository intelligence | Compose `repo-intelligence` receives only the settings `compose.yaml` lists, not `.env`, reads each tenant's bundle and the checkouts through the read-only mounts `inv repos-compose` writes, the bundle at `config/local/tenants/<tenant>/` and each checkout at `/tenants/<tenant>/repositories/<repo>`, and derives each tenant's token from `REPO_INTELLIGENCE_TOKEN_KEY`. `inv k8s-reload` gives each tenant's worker its token as `REPO_INTELLIGENCE_TOKEN`. A rotation changes `REPO_INTELLIGENCE_TOKEN_KEY` in `.env` and runs `inv k8s-reload`, which recreates `repo-intelligence` and restarts every tenant worker and gateway | ECS `repo-intelligence` reads each tenant's bundle from the tenant config bucket and the checkouts the tenant's worker keeps on the tenants access point, mounted read-only at `/tenants`. It receives the ARN of each tenant's `<name_prefix>/tenants/<tenant>/repo-intelligence-token` in `REPO_INTELLIGENCE_TOKEN_SECRET_ARNS`, reads the AWSCURRENT and AWSPREVIOUS versions with its task role, and accepts both. The secret-store token rotation function replaces the token every `repo_intelligence_token_rotation_days`, 30 by default, and the restart automation then restarts the tenant's activity worker and MCP gateway, which receive the token through their SecretProviderClass |
| MCP gateway | `mcp-gateway` in `tenant-<tenant>` under the worker's service account, with a ClusterIP Service reached through `kubectl -n tenant-<tenant> port-forward svc/mcp-gateway 8150:80`. Its `MCP_GATEWAY_TOKEN` comes from `.env` for the home tenant and from `config/local/tenants/<tenant>.env` for every other tenant, and the render refuses a tenant without its own token or two tenants with the same one | The same deployment behind an internal ALB Ingress per tenant, from `eks_mcp_gateway_certificate_arn` and `eks_mcp_gateway_client_cidrs`, with `MCP_ALLOWED_HOSTS` set to that load balancer's host name. Its token is `<name_prefix>/tenants/<tenant>/mcp-gateway-token`, which the [tenant](../infra/terraform/tenant) module generates and only the tenant's worker role reads |
| Webhook routing | With more than one tenant, the inbound webhook reads each tenant's `repositories.yaml` and `jira.yaml` from a ConfigMap and each tenant's `GITHUB_WEBHOOK_SECRET` and `JIRA_WEBHOOK_SECRET`, taken from its settings file, from the Secret `inbound-webhook-tenants`. A repository several tenants list is served to each, and the webhook routes each pull-request delivery to the tenant whose secret verifies it. Jira deliveries arrive at `/webhook/jira/<tenant>` | With two or more tenants, the [tenant](../infra/terraform/tenant) module creates `<name_prefix>/tenants/<tenant>/github-webhook-secret` and `jira-webhook-secret` under the tenant key, empty until an operator stores the value and readable only by the inbound webhook role, which also reads `tenants/<tenant>/` of the tenant config bucket |

## Cross-cutting infrastructure

These modules provision the shared AWS infrastructure the components above consume. The [private-bedrock](../infra/terraform/examples/private-bedrock) composition root wires them into one apply for a single account.

| Concern | AWS target | Provisioning module |
|---|---|---|
| Private connectivity | Shared VPC interface and gateway endpoints behind one security group | [vpc-endpoints](../infra/terraform/vpc-endpoints) |
| Container registry | ECR repository with scan-on-push, immutable tags, and a lifecycle policy | [ecr](../infra/terraform/ecr) |
| Audit trail | CloudTrail with its own S3 bucket | [cloudtrail](../infra/terraform/cloudtrail) |
| Bedrock inference authorization | `bedrock:InvokeModel` IAM policy | [bedrock-iam](../infra/terraform/bedrock-iam) |
| Container platform | Shared ECS cluster on Fargate that the platform owns, with encrypted Exec sessions and ephemeral storage | [ecs-cluster](../infra/terraform/ecs-cluster) |
| Kubernetes platform | EKS cluster with a private API endpoint, a platform and a tainted sandbox node group on arm64, network policy enforcement, and Pod Identity roles for the workloads that call AWS | [eks-cluster](../infra/terraform/eks-cluster) |
| Service-to-service HTTPS | One internal ALB under the FIPS TLS policy with host routing to each service, re-encrypting to every task, and a private hosted zone | [container-services](../infra/terraform/container-services) |
| Off-hours schedule | EventBridge Scheduler and SSM Automation that scale the ECS services to zero overnight so Aurora pauses | [off-hours](../infra/terraform/off-hours) |
| Laptop Bedrock path for test accounts | Ephemeral ECS Fargate jump-host reached over ECS Exec, in the management tier | [bedrock-jumphost-fargate](../infra/terraform/bedrock-jumphost-fargate) |
| Network tiers | Public, application, management, and data subnets with per-tier route tables and a data-tier network ACL | [private-bedrock](../infra/terraform/examples/private-bedrock) |
| Outbound internet | NAT instance or NAT Gateway for the application and management tiers | [egress](../infra/terraform/egress) |
| Outbound destination filtering | Route 53 Resolver DNS Firewall allowlist with query logging | [dns-firewall](../infra/terraform/dns-firewall) |
| Terraform state | Versioned, encrypted S3 bucket with S3 native locking | [tf-state](../infra/terraform/tf-state) through [bootstrap](../infra/terraform/bootstrap) |
| Bucket access logging | S3 bucket receiving server access logs from every platform bucket | [access-logs](../infra/terraform/access-logs) through [bootstrap](../infra/terraform/bootstrap) |
| Tenant cost attribution | The `tenant` tag on every tenant resource, activated once per payer account as a cost allocation tag in AWS Billing. ## Secret material

The Temporal clients read `TEMPORAL_HOST`, `TEMPORAL_NAMESPACE`, `TEMPORAL_TLS_SERVER_NAME`, and `TEMPORAL_TLS_CA` from the `temporal_client` output of the [private-bedrock](../infra/terraform/examples/private-bedrock) root. Locally the last two are empty and the clients connect without TLS. The Temporal TLS certificates and keys live in Secrets Manager under a key the [temporal-control-plane](../infra/terraform/temporal-control-plane) module creates, and `inv temporal-certs put` writes them.

Local secrets live in `.env` and the `config/local/*.yaml` operator files. In a deployed environment they live in AWS Secrets Manager, provisioned by the [secret-store](../infra/terraform/secret-store) module and injected into each task as environment values. The review and authorship signing keys arrive as `REVIEW_SIGNING_KEY` and `AUTHORSHIP_SIGNING_KEY` in place of the local key files. The LiteLLM master key, the Langfuse keys, the ClickHouse password, the GitHub and Jira tokens and webhook secrets, and the per-service database and cache credentials are the other secret values. The module README lists each one with its rotation. Each tenant's own credentials, which are its GitHub and Jira tokens, authorship signing key, registry token, Slack webhook, and MCP gateway token, live under `<name_prefix>/tenants/<tenant>/` instead, created by the [tenant](../infra/terraform/tenant) module, and reach only that tenant's worker identity, which the tenant's worker and MCP gateway run under, in place of the platform's copies. With two or more tenants, each tenant's GitHub and Jira webhook secrets live under the same prefix and reach only the inbound webhook. Repository intelligence reads each tenant's repository intelligence token at runtime with its task role rather than receiving it as an injected value. LiteLLM receives its database credential as `DATABASE_USERNAME` and `DATABASE_PASSWORD` and builds its connection URL from them and from `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME`, `DATABASE_SSLMODE`, and `DATABASE_SSLROOTCERT`. Locally it reads a `DATABASE_URL` that the local cluster render derives from the platform `DATABASE_URL`, with the `litellm` database in place of `agent_platform`. The trust-root bundle at `REVIEW_TRUST_ROOT_PATH` holds only public keys and ships as a non-secret configuration artifact.

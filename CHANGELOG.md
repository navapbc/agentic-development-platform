# Changelog

All notable changes to this platform are recorded here. The format follows Keep a Changelog, and the platform aims to follow semantic versioning once releases are tagged.

## 0.3.0 (unreleased)

AWS transition and FedRAMP Medium readiness. The platform documents its local-to-AWS mapping and its FedRAMP Medium control posture under the AWS shared-responsibility model, commits the audit and evidence contracts, persists evidence and audit records to a write-once-read-many object store, and provisions a tiered network, a filtered egress path, the data tier with encryption, private placement, and backups, and a secret store with per-service database roles and scheduled credential rotation.

### Breaking changes

- The Jira Cloud ticket source calls the Jira REST API v3 with the site's account email and API token, and the platform no longer uses the Atlassian CLI. `INSTALL_ACLI`, `ACLI_VERSION`, `ACLI_SHA256`, `ACLI_DOWNLOAD_URL`, and `JIRA_ACLI_PATH` are no longer read, `inv fetch-acli` and the `--install-acli`, `--acli-version`, and `--acli-sha256` options of `inv publish-platform-images` are removed, and the intake schedule pauses when a Jira Cloud site refuses the account email and token, in place of when acli is missing. Remove the settings from `.env`.
- Every image the platform builds runs on Amazon Linux 2023 minimal, pinned by digest in `docker/al2023/versions.env`. The platform and eks-deployer images run Python 3.12 and repo-intelligence runs Python 3.13 from the Amazon Linux packages, repo-intelligence and the Java tooling use Corretto 21 and Maven 3.8.4 from the Amazon Linux packages, and the builder image runs the Amazon Linux buildah 1.43.1. The example gate engines start `FROM` the same base, so a local `image_policy.yaml` admits `public.ecr.aws/amazonlinux/`.
- Every image a tenant pod runs needs an `@sha256:` digest and a repository `config/<env>/image_policy.yaml` admits, and a worker refuses a config bundle that names any other image. Copy `config/local/image_policy.yaml.example` to `config/local/image_policy.yaml`, then run `inv runtime-images` and `inv gate-engine-images`, which write the digest-pinned `RUNTIME_IMAGES`, `GATE_ENGINE_BUILDER_IMAGE`, and `GATE_ENGINE_IMAGES` into `.env`. In AWS the `private-bedrock` root generates the policy.
- A gate engine source Dockerfile and a repository's checks `build:` Dockerfile pin every image they pull by `@sha256:` digest, the `FROM` base of each stage, each `COPY --from` image, and each `RUN --mount` `from=` image. Each one passes the image policy and the scan gate before the pod starts, and a build that names an image without a digest, or through an `ARG` with no default, is refused.
- `inv publish-platform-images` publishes nothing when it finds no signing profile in `--signing-profile`, `IMAGE_SIGNING_PROFILE_ARN`, or the root's `image_signing_profile_arn` output. Pass `--unsigned` for a deployment that does not verify signatures, and set the `AWS_IMAGE_SIGNING_PROFILE_ARN` repository variable for the `publish-images` workflow.
- The gate, checks, and scanner pods run the platform's buildah image, `docker/buildah.Dockerfile`, which `inv publish-platform-images` builds into the `buildah` repository instead of copying the upstream buildah image.
- `inv publish-platform-images` scans every image with the Amazon Inspector SBOM generator and Scan API before it pushes it, and pushes nothing while an image carries a HIGH or CRITICAL finding `--exceptions` does not accept. The publishing identity needs `inspector-scan:ScanSbom`, which the GitHub publisher role now holds.
- A tenant's `gate_engine.yaml` may not define an engine named `security-policy` or `test-policy`, which are now catalog engines. Remove those entries and enable the engines by name in `gates.yaml`.
- An activity worker refuses to start without `TENANT`, the tenant it serves. Add `TENANT=adp`, or the tenant's name, to `.env`.
- `create_eks` in `private-bedrock` needs at least one entry in the new `tenants` map, because every run belongs to a tenant and the deployment has no default tenant. Add a tenant for the existing team, as `tenants.tfvars.example` shows.
- Each tenant's activity worker runs in its own `tenant-<tenant>` namespace and creates its sandbox, gate, checks, and scanner pods in `tenant-<tenant>-sandbox`. The EKS and local deploys stop rendering the activity worker in the platform namespace and the `agent-sandbox` namespace and delete them, with the platform `workspaces` claim and the `agentic-platform-checkouts` volume. Set `TENANTS` in `.env` to the local tenants, `TENANTS=adp` for a workstation with `TENANT=adp`. A local checkout from before tenants is not carried over, so run `inv repos-sync` after the first deploy.
- `private-bedrock` drops `create_rebar_ticket_store` and the `rebar_ticket_store_*` variables and outputs, because each tenant owns its ticket store. Move `rebar_ticket_store_writer_oidc_trust` to the tenant's `ticket_store.writer_github_oidc_trust` and the trusted principals to `ticket_store.operators`, and point the reconcile-bridge workflow's `AWS_BRIDGE_ROLE_ARN` and `TICKETS_S3_URL` at the tenant's writer role and bucket from the `tenants` output. The apply destroys the untenanted store, so copy any tickets out of its bucket first.
- The intake and reap schedules belong to tenants. Each tenant's worker installs `<source>-intake-<tenant>` and `orphan-reaper-<tenant>` on its task queue at startup, and the `schedule-bootstrap` task and `inv schedules-install` now remove the untenanted schedules instead of installing them. A platform setting may no longer be named `TENANTS`, which the container-services module sets.
- An enabled entry in `gate_engine.yaml` must set `review_entrypoint`, and `classifier_entrypoint` defaults to empty, which runs no test classifier. The defaults named the harness paths of one external engine repository. Add both paths to an entry that relied on them.
- The `private-bedrock` composition root stores its state in the S3 backend. Before any plan or apply, run the `infra/terraform/bootstrap` root, write `backend.hcl` from its `backend_hcl` output, and run `terraform init -migrate-state -backend-config=backend.hcl` in the composition root. An apply against the empty remote state tries to recreate the stack, which duplicates the VPC and subnets and fails on names that already exist.
- Every Terraform root and module requires Terraform 1.11 or later, AWS provider 6.50 or later below 7, and random provider 3.7 or later below 4 where it is used. Upgrade the local Terraform binary. A working directory whose lock file pins an older provider needs `terraform init -upgrade`, with `-backend-config=backend.hcl` in a root that uses the S3 backend. The `private-bedrock` root also adds the archive provider, so run `terraform init -backend-config=backend.hcl` before the next plan.
- The `elasticache` module writes the cache user password through write-only arguments and drops the random provider. An existing cache user receives a new password, and its secret a new version, on the next apply. Restart Langfuse after that apply.
- Remove `REBAR_LLM_MODEL` from `.env`. rebar 0.13 raises `RemovedInputError` when `LLMConfig.from_env` finds it. The review gates build their model configuration in code and never read it, so a path that calls `LLMConfig.from_env` was the only one it broke.
- With `create_network = true`, the next apply adds an internet gateway, a NAT instance, and the DNS Firewall with `dns_firewall_default_action = "BLOCK"`. A workload in the VPC that resolves a name outside the allowlist receives NXDOMAIN. Add its domains through `dns_firewall_additional_domains`, or apply with `ALERT` first and review the query log. Existing-network deployments keep no egress path and no DNS Firewall.
- The local cache, ClickHouse, and Langfuse upgrades are one-way. On the first start, Valkey rewrites the cache snapshot in a format Redis 7.4 rejects, ClickHouse upgrades its data in place without downgrade support, and Langfuse 4.59.0 migrates its Postgres and ClickHouse schemas. A checkout without this release, including another branch, fails Langfuse on its next `up` until the cache snapshot, the ClickHouse volume, and the `langfuse` database are restored. Take the cache, ClickHouse, and `langfuse` database backup in the README section on Langfuse backing services before the first start.
- The local cache disables its default user. A client authenticates as `REDIS_USERNAME`, which defaults to `langfuse`, with `REDIS_AUTH`, so `redis-cli -a` with only a password and any password-only client are refused. Connect with `docker compose exec redis sh -c 'valkey-cli --user "$REDIS_USERNAME" --pass "$REDIS_AUTH"'`.
- `litellm-config.yaml`, `litellm_redaction.py`, and `rebar-review.toml` move from `config/local` to `config/platform`. Stash uncommitted edits to the old files before `git pull` and reapply them under `config/platform`. Update personal compose overlays and shell exports of `REBAR_LLM_CONFIG_FILE` that name the old paths. Gate model resolution reads `config/platform/litellm-config.yaml` in every environment and no longer reads a per-environment `config/<env>/litellm-config.yaml`.
- `db-migrate` and `schedule-bootstrap` run under the `tasks` profile, so `docker compose up` no longer migrates the database or registers schedules. Start the stack with `inv local-up`, which builds the images, runs the migrations, and starts the services. Register the schedules once with `inv schedules-install`. A plain `docker compose up -d` leaves the workers and `coordination-service` waiting with `Run inv db-migrate` in their logs. Remove the exited containers an earlier `up` left behind with `docker compose rm -f db-migrate schedule-bootstrap`.
- The intake schedule is named for its source, `jira-intake` or `rebar-intake`. Run `inv intake --schedule` or `inv schedules-install` after upgrading. Installing the `rebar-intake` schedule deletes a `jira-intake` schedule left from the shared name. `inv intake` accepts `--source jira` or `--source rebar`, which defaults to `TICKET_BACKEND` and is refused when it names the other source.
- `inv rebar-poll` is now `inv rebar-changes`. It runs in the activity-worker container, reports changes without moving the intake cursor, and no longer accepts `--report-only`.
- `compose.local.yaml` is removed. The `registry` service is in `compose.yaml` under the `registry` profile. Start it with `docker compose --profile registry up -d registry`.
- Every Terraform module that creates an S3 bucket requires `access_log_bucket`, and S3 server access logging is always on. This covers `tf-state`, `evidence-store`, `langfuse-blob-store`, `cloudtrail`, and `bedrock-jumphost-fargate`. Apply the `bootstrap` root again so it creates the access-log bucket, then set `access_log_bucket` in each composition root's tfvars to the value of `terraform output -raw access_log_bucket`. A plan without it fails variable validation.
- The `ecr` module encrypts the repository with a customer-managed KMS key and no longer accepts `image_tag_mutability` or `scan_on_push`, which are fixed to `IMMUTABLE` and `true`. A changed encryption key replaces an existing repository, and `force_delete` lets that apply delete the repository with its images. Push the jumphost image again with `inv publish-jumphost-image` after the apply.
- The platform services bind to `BIND_HOST`, which defaults to `127.0.0.1`. The platform and repository-intelligence images set `BIND_HOST=0.0.0.0`, so containers behave as before. A service started on the host listens on loopback unless `BIND_HOST` is set.
- The Kubernetes base manifests name their images `123456789012.dkr.ecr.us-east-1.amazonaws.com/agentic-dev-platform/<service>:0.3.0` in place of `REGISTRY/agentic-dev-platform/<service>:latest`, and run with a read-only root filesystem and an `emptyDir` at `/tmp`. A kustomize overlay that rewrites the old image name must match the new name.
- The worker images no longer install `acli` unless `INSTALL_ACLI=true` is set in `.env`. A Jira Cloud ticket source needs it, so set `INSTALL_ACLI=true` and run `inv local-up` to rebuild. Without it the Jira Cloud path fails with an error that names `INSTALL_ACLI`. Rebar and Jira Data Center do not use acli.
- Python dependencies install from a committed `uv.lock` through uv 0.13.3 or newer. Replace `pip install -e ".[dev,...]"` with `uv sync --locked --all-extras`, which also removes packages the lock does not list from `.venv`. Change a dependency with `uv lock` or `uv lock --upgrade-package <name>` and commit the lock. CI and both image builds refuse a stale lock.
- The draft pull request workflow schedules a `record_plan_evidence` activity at plan acceptance, so its history changes. An execution that is in flight across the upgrade and has already passed plan acceptance blocks on a non-determinism error when the new worker replays it, because the new command does not match the event its history recorded at that point. An execution parked at or before the plan gate is unaffected, since the new command is appended to history with nothing to contradict it. Let the late-stage executions finish before deploying, or terminate and restart them. Worker versioning covers them only if workers running the previous build keep polling the task queue until those executions drain, so setting `WORKER_VERSIONING_ENABLED=true` and a new `AGENT_BUILD_ID` at the same deploy is not on its own sufficient. This release turns worker versioning on by default, which pins the executions that start after the drain and leaves the ones already in flight unpinned.
- Temporal worker versioning is on, through Worker Deployments. `WORKER_VERSIONING_ENABLED` defaults to true and `WORKER_DEPLOYMENT_NAME` to `agent-platform`. Each worker registers as a version of that deployment with the default versioning behaviour `PINNED`, and makes its version current once it polls, so executions that start afterwards route to it and executions already running stay on the version that started them, across every task queue that version serves. Remove `AGENT_BUILD_ID` from `.env`. The worker image bakes the identifier through a Dockerfile `ARG`, which `inv local-up` passes as a build argument, and an `AGENT_BUILD_ID` line in `.env` would override it. `inv local-up` derives the identifier from a digest of the image sources and records it in `.build-id.json`, so a rebuild of unchanged sources reuses its identifier and consumes no new version. Host tasks read that file. `config/platform/temporal-dynamic-config.yaml` is removed, because Worker Deployments need no dynamic config entries, so run `inv local-up` to recreate the Temporal container. A version the server keeps counts against the per-deployment version ceiling, and `inv prune-worker-versions` deletes every drained one. Executions already in flight carry no deployment version, and enabling versioning does not pin them after the fact, so drain them once before the first versioned deploy. An environment that cannot run versioning sets `WORKER_VERSIONING_ENABLED=false`.
- The platform image installs its packages into `/opt/venv` from the new `worker` extra, which holds the extras it installed before plus `pydantic-ai-slim[openai]` and `ruff`. A derived image that adds a Python library the platform imports must install it into `/opt/venv`, for example with `uv pip install --python /opt/venv/bin/python <package>`. A command-line tool installed with the system `pip`, such as the scanner example in `docs/gate-engine.md`, still lands on `PATH`.
- The local Temporal server moves from `temporalio/auto-setup:1.29.7` to `temporalio/server:1.32.1`, and the schema change is one-way. `inv local-up` refuses a database whose schema predates server 1.31. Run `inv temporal-upgrade` once on an existing stack. It backs up the `temporal` and `temporal_visibility` databases to `~/temporal-backup/<UTC time>` with `pg_dump`, then runs servers 1.30.8, 1.31.4, and 1.32.1 in turn, applying each release's schema before its server starts. Restoring a 1.29.7 server requires restoring both databases from that backup, as the README describes. `docker compose up` alone no longer applies the Temporal schema or registers the `default` namespace.
- The `inbound-webhook` and `mcp-gateway` Ingress resources declare an HTTPS-only listener set and no longer provision an HTTP:80 listener. Issue an ACM certificate for each hostname, patch `alb.ingress.kubernetes.io/certificate-arn` on both Ingress resources from the environment overlay as described in `deploy/kubernetes/README.md`, and change the GitHub webhook URL to `https://<webhook-hostname>/webhook/pr` and the Jira webhook URL to `https://<webhook-hostname>/webhook/jira`. An `http://` webhook URL stops delivering, and GitHub does not re-send a POST body across a redirect, so no HTTP listener is provisioned to redirect from.
- The coordination service requires `COORDINATION_SHARED_SECRET` and refuses to start while it is empty. Set it in `.env`, where the workers read the same value and present it on every coordination call. `inv config-check` reports the key when it is absent from the process environment and from `.env`, so an environment created before this release surfaces the gap before `inv local-up`. `CoordinationClient` refuses to construct with an empty token, and it maps a 401 from the service to an error naming the variable, the env file, and `inv local-up`. The `secret-store` module generates a `coordination_shared_secret` for a deployed environment. Compose no longer publishes port 8130 to the host, so the RPC is reachable only from the Compose network. Reach it for debugging with `docker compose exec coordination-service python -m services.healthcheck http 8130`.
- An integration whose mode in `config/<env>/integrations.yaml` is `webhook` or `hybrid` requires its signing secret, `GITHUB_WEBHOOK_SECRET` for `pr_closed` and `JIRA_WEBHOOK_SECRET` for `jira_intake`. The inbound webhook service exits at startup naming the missing variable. An empty secret previously accepted every delivery as verified. Polling mode, which both integrations ship with, is unaffected.
- `config/<env>/repositories.yaml` lists the source-control repositories and is required. Each entry names its backend, `github` or `local`, its default branch, whether repository intelligence indexes it, and its checkout path. Copy `config/local/repositories.yaml.example` and list each repository. The GitHub allowlist, the indexed repositories, the promotion policy's `allowed_repos` input, and the per-repository backend are all read from it.
- `SOURCE_CONTROL_BACKEND`, `SOURCE_CONTROL_LOCAL_ROOT`, `SOURCE_CONTROL_LOCAL_REPOS`, `REPO_INTELLIGENCE_REPOS`, `REPO_INTELLIGENCE_REPO_ROOT`, `REPO_INTELLIGENCE_COMMIT`, and `GITHUB_DEFAULT_BASE_BRANCH` are removed. A process that finds one of them in its environment or in `.env` refuses to start and names the `repositories.yaml` field that replaced it. Move each value into `repositories.yaml` and delete the setting.
- `github.yaml` is version 2. Its `allowlist` and `repositories` sections move to `repositories.yaml`, and a file that still sets either is refused. Move each repository override of `host`, `owner`, or `token_ref` onto the repository's entry in `repositories.yaml` and set `config_version: 2`.
- The demo repository mounts leave `compose.override.yaml`. `inv local-up` runs the new `inv repos-compose`, which writes the git-ignored `compose.repositories.yaml` from `repositories.yaml`. A personal override that mounted repositories under `/repos` drops those mounts.
- The promotion policy bundle is version 0.5.0 and no longer carries a default repository list. A decision input without `allowed_repos` allows no repository.
- The `container-services` module and the `private-bedrock` root no longer accept `repo_intelligence_repos` and `container_repo_intelligence_repos`. Remove them from the tfvars file and add `repositories.yaml` to the directory in `container_config_dir`.
- The activity worker, the review worker, LiteLLM, and OPA run in the local Kubernetes cluster and leave Compose, and the `langgraph-service` Compose service is removed. Enable Kubernetes in Docker Desktop, or set `K8S_CONTEXT`, `K8S_COMPOSE_ADDRESS`, and `K8S_IMAGE_LOAD` for another cluster, then run `inv local-up`, which deploys them after Compose. No pod mounts a host directory, so a source edit reaches the cluster workers through `inv k8s-reload`, and `inv logs --service NAME` follows a cluster deployment.
- The cluster workers start on a new `workspaces` volume. Executions in flight under `.agent-workspaces` do not carry over, so finish or abandon them before upgrading. The rebar ticket store is created on the volume from its bucket at worker start.
- LiteLLM and the review worker no longer mount `~/.aws`. Run `inv aws-login`, which `inv local-up` runs, to write the credentials of `PLATFORM_AWS_PROFILE` to the cluster, and run it again when they near expiry. A profile that signs in through Kion or another helper needs `AWS_LOGIN_COMMAND`.
- A repository with backend `local` is copied into the cluster by `inv repos-sync`, and the agent commits to that copy. Run `inv fetch-results` to bring the agent branches back into the checkout at `path`. `inv operator-done` runs it first.
- The local backend commits each run's `SUMMARY.md`, `change.patch`, and pull record to `refs/agent-results/<branch>` in the repository, in place of files under `SOURCE_CONTROL_LOCAL_ARTIFACTS_ROOT`, which now holds only the `inv operator-done` ledger.
- `local_path` of a local-mode engine in `gate_engine.yaml` names the engine checkout on the host, absolute or relative to the platform checkout, and `inv repos-sync` copies its working tree into the cluster. Replace a container path such as `/engines/ai-common-workflows` with the host path.
- `OPA_HOST_PORT` and `LANGGRAPH_HOST_PORT` are removed and OPA has no host port. `inv smoke-test` checks OPA through `kubectl exec`. The `docker compose` commands that named `activity-worker` run against the cluster instead, through `kubectl exec` on the deployment.
- The MCP gateway requires `Authorization: Bearer <MCP_GATEWAY_TOKEN>` on every `/mcp` request and answers any other request with 401, and it refuses to start while `MCP_GATEWAY_TOKEN` is empty. Set `MCP_GATEWAY_TOKEN` in `.env`, run `inv k8s-deploy`, and give each MCP client the same value. The health paths answer without it.
- The `mcp-gateway` Ingress sets `alb.ingress.kubernetes.io/inbound-cidrs` to the documentation range `192.0.2.0/24`, which admits no client. Patch it to the client subnets in the environment overlay.
- `inv publish-platform-images` writes the image references to `images.auto.tfvars.json` in the `private-bedrock` composition root, which Terraform reads with no flag. Remove the seven `container_*_image` variables from the tfvars file, because a `-var-file` value overrides the file and would keep the old references.
- The `container-services` input `bedrock_invoke_policy_arn` is replaced by the list `bedrock_invoke_policy_arns`, and the `temporal-control-plane` output `ui_service_arn` by the list `service_arns`, which holds the server and UI services. A caller outside `private-bedrock` passes the policy ARN as a one-element list.
- Each ECR repository the `ecr` module creates keeps the 5 most recently pushed images tagged `-arm64` and, separately, the 5 most recently pushed images tagged `-amd64`, set by `retained_image_count`, and the next apply expires older tagged images and their signatures. The policy keeps the newest `retained_signature_index_count` notation referrers indexes, 100 by default, which protect the signatures of the retained images, keeps the newest `retained_image_count` images with any other tag, and still expires untagged images after `untagged_expiry_days`. Raise `retained_image_count` before the apply if a deployment pulls an older image.
- Every finding exception entry requires `config_version: 1`, a non-empty `reason`, a `created` date, and an `expires` date no more than 30 days after `created`. A platform entry also requires `requester` and `approver`. The pre-push scanner and the tenant worker share one parser, so a file whose entries lack these fields is refused.
- The platform exceptions file accepts findings only in images the platform publishes or defines, the `catalog` entries and the `platform_registries` repositories outside `tenant_prefix`. Exceptions for tenant images belong in the tenant bundle's `image_exceptions.yaml`. An entry outside its file's scope is refused with an error that names it.
- In AWS the worker and both publish commands read the platform exceptions from `platform/image_exceptions.yaml` in the tenant config bucket. The `private-bedrock` root no longer sends `image_exceptions.yaml` from `container_config_dir`, and the plan fails while that directory holds the file. `--exceptions` on the publish commands now names a local file read in place of it.
- The tenant config bucket policy statement `DenyObjectsOutsideATenantPrefix` is renamed `DenyObjectsOutsideTheTenantAndPlatformKeys`, and it admits the `platform/image_exceptions.yaml` and `platform/image_policy.yaml` keys.

### Added

- The local collector writes the exported platform log records to rotated JSON files on the `otel-logs` volume, and `inv platform-logs [--match TEXT]` prints them.
- `inv intake --retry` records an `intake_retry` audit event listing the intake records, work claims, and stale executions it clears, before it clears them.
- The `publish-images` workflow builds in parallel. A `base` job pushes the hardened base and the CIS scanner to the new `al2023-base` and `al2023-openscap` repositories, one job per `PUBLISH_GROUPS` entry builds, scans, and pushes its images, and the `publish` job merges them, signs, and writes the references. `inv publish-platform-images` gains `--stage`, `--group`, `--partial`, and `--partials` for these jobs.
- The `publish-images` workflow runs daily on the default branch, where it rebuilds, scans, and publishes the platform images for arm64, and an operator deploys with `inv aws-release`. A `report` job writes a run report to the job summary and uploads it, with the scan logs, as the `image-report-<arch>` artifact.
- The daily run reads the newest release of each component that `docker/al2023/versions.env` pins with `scripts/upstream_releases.py`, from GitHub releases, the version tags of a repository without releases, go.dev, or the Amazon Linux release tags in ECR Public, retrying a rate-limited answer and, once, a request whose token GitHub refuses without the token, and it scans the upstream image of each component built from source with `inv image-scan`. A release newer than its pin, and whether its image scans clean, appear in the run report, and an unreachable release API is reported without failing the publish.
- The daily exception review reads the platform file and every tenant file. It removes expired and resolved platform entries with a conditional put, reports each removal with the new object version, and emits `::error::` with a warning at the top of the report when a file is missing or unreadable.
- A tenant config bundle may hold `image_exceptions.yaml`, which accepts findings in images under the tenant's `tenant_prefix` and its `registries.yaml` mirrors. `inv tenant-config-validate` and `inv tenant-config-publish` apply the scope and field checks.
- The `image-exception` workflow, manually dispatched with `image`, `finding`, `reason`, and `expiry`, runs in the `image-exception` GitHub environment. It checks scope and expiry, confirms the finding with `inv image-scan`, and records `github.actor` as the requester and the approving reviewer as the approver. It writes `platform/image_exceptions.yaml` with a conditional put.
- `inv image-exceptions-add` and `inv image-exceptions-prune` edit the local platform or tenant exceptions file with `--scope platform|tenant`. Both refuse to run while `TENANT_CONFIG_BUCKET` is set. `inv local-up` warns when the platform exceptions file is missing or unreadable.
- The `tenant-config-store` module creates `platform/image_exceptions.yaml` once and never overwrites it, optionally writes `platform/image_policy.yaml`, and outputs `platform_exceptions_read_policy_arn` for the tenant workers.
- The `github-image-publisher` module accepts `config_store`. The publish role can then prune the platform exceptions and read the tenant ones, and the module creates an `image-exception` role that trusts only the `image-exception` environment. The `private-bedrock` root outputs `config_bucket` and `github_image_exception_role_arn`.
- A local-to-AWS mapping document that maps each local component to its AWS target and the Terraform module that provisions it.
- Committed JSON-schema contracts for the audit-event and the evidence-object shapes, with a conformance test that validates the producer write shapes against them.
- An S3-backed write-once-read-many evidence and audit object store. When `EVIDENCE_OBJECT_STORE_ENABLED` is set, each evidence object and each audit event persists to an S3-compatible store under Object Lock, content-addressed and idempotent, and the Postgres row records the object location. The activity and review workers run a startup preflight that fails fast when the store is enabled without a reachable, Object-Lock-enabled bucket.
- An `evidence-store` Terraform module that provisions the bucket with Object Lock, KMS or AES256 encryption, a TLS-only and writer-allowlist policy, a public-access block, versioning, and access logging.
- An `inv evidence-bucket-bootstrap` task that creates the local Object-Lock bucket for a MinIO opt-in, and `EVIDENCE_OBJECT_STORE_*` settings.
- A FedRAMP Medium hardening design that ties each component to its control families under the AWS control-inheritance model.
- A FedRAMP control inheritance and shared-responsibility matrix that records the inherited, platform-implemented, and deploying-organization controls per family.

### Fixed

- An intake pass whose workflow start failed after the execution row was seeded no longer drops the ticket. - structlog events, among them the rebar poll audit events and the orphan reclaims, reach the OTLP log export, and `inv intake` exports its own records, so an operator command run in the worker pod is logged the same way. They previously printed to stdout only and were lost with the pod.
- Two intake passes that overlap, such as a retried pass and the next scheduled one, start one run per ticket. `run_once` claims a side effect exclusively, so a second caller finds it in flight and defers the ticket to the next pass, which replays the first start, and the inbound webhook answers a delivery still in flight with 409. A claim whose holder stopped is taken over after 300 seconds, and a claim whose effect raised is released at once.
- An activity whose worker stops, as every worker does on a redeploy, is retried once its heartbeats stop, in place of holding the run until the activity's start-to-close timeout. Every worker heartbeats each running activity every 30 seconds, and every activity scheduled without a heartbeat timeout receives one of 3 minutes. The implementation stage retries only after a lost worker, on a workspace reset to its materialized commit, and a retried stage replaces the sandbox pod the lost attempt left. The retry starts with the stage's whole cost budget, so the stage can spend up to twice `max_cost_usd` when its worker is lost, and a worker lost within 3 minutes of the stage timeout is treated as a timeout and not retried. The gate, checks, and scanner pods replace a pod an earlier attempt left in place of reusing it.

The inbound webhook service refuses to start when an integration runs in webhook or hybrid mode without its secret, which covers the configuration present at start. A mode switched to webhook afterwards without a secret is refused at request time, because verification fails closed.
- The parked-execution reconciler can find a newer build, and `inv resume-parked` now moves the execution onto it. `AGENT_BUILD_ID` held the constant `dev`, out of which `is_newer_build` read no digits, so `inv resume-parked` and every `AWAITING_FIX` park refused to resume whatever the deployed build was. The image now bakes an identifier that grows with each build, so an environment that does not run `inv local-up` ranks a redeploy as newer too. Finding the newer build was not enough on its own, because the resume signal left the execution pinned to the build that parked it, so it either replayed the code it parked to escape or stalled when that build's workers had stopped polling. The task now repins each execution to the current deployment version before it signals, which `WORKER_VERSIONING_ENABLED=false` skips along with the rest of versioning.
- `alembic_database_url` derives its fallback from `DATABASE_URL` in place of a literal that carried the example password, so a host-run `inv smoke-test` or `inv db-reset` authenticates with the configured credentials. The `database_url` default names the `postgres` service, which the host rewrite maps to the published port.
- `inv workflow-status` resolves `TEMPORAL_HOST` through the host rewrite, so it reaches the published Temporal port in place of failing on the Compose service name.
- `inv db-migrate`, `inv schedules-install`, and `inv db-reset` build their image before running. `inv local-up` builds only the services it starts, so the `tasks` profile previously reused whatever `db-migrate` image was left in the local cache.
- The draft pull request orchestrator settles its work claim on every outcome it returns. A completed run marks the claim completed, and a failure, a cancelled promotion, or an abandoned repair releases it. A cancellation that arrives while the workflow waits at a gate settles no claim, and `inv restart` drops the row. Each attempt records a `WORK_UNIT_SETTLED` audit event, so a claim that cannot be settled is visible without reading the table. The claim was previously released only on the human-intervention alert path, and the release was addressed to the implementation child workflow rather than the parent that holds the claim, so no outcome released anything and the work unit stayed locked until an operator edited the table.
- `inv restart` drops a stranded work claim even when the intake dedup record is already gone, and reports the dropped claims separately from the dropped intake records. The count it reported previously covered intake records alone while reading as though it covered claims.
- `inv intake --retry` and `inv restart` release the rebar poll watermark as well as the intake dedup record. The rebar poll is edge-triggered on a per-ticket revision in `<repo_root>/.rebar-poll-watermark.json`, so clearing only the side-effect ledger left the ticket invisible to every later pass, which logged `rebar_poll_noop` while the retry reported success. A retry that releases only the watermark now also counts as retriggered, fails the ticket's stale executions, and resets the sequence gate. The release is recorded as a uniquely named marker file under `<repo_root>/.rebar-poll-releases/` that the next pass honours as it loads the cursor, and a pass deletes only the markers it read, so a release that arrives mid-pass takes effect on the following pass rather than being dropped. The retry reports when the watermark file is missing at the configured path, when the cursor no longer holds the ticket, and when the rebar store does not list the ticket as ready, in place of withholding the retry. `inv intake --retry` exits non-zero when nothing was retriggered, matching `inv restart`.
- `tickets.yaml` requires `backend.repo_root` to be an absolute path. Operator commands resolve it on the host while the intake poll resolves it inside the worker container, so a relative path named a different store in each.
- The rebar change report no longer saves the cursor the rebar intake pass reads. A ticket the report listed was previously treated as already seen and never started.
- Slack alert delivery and the `acli` download refuse any URL that is not https, including a redirect to http. The Slack sender previously accepted a `file:` URL.
- The sandbox copy-in and patch extraction quote the project path in the pod shell command.
- The scanner pod writes the tool report to a `mktemp` file in place of a fixed `/tmp` path.
- The Postgres init script passes each database name to psql as a variable and quotes it with `format('%I')` in place of interpolating it into SQL, and splits the list without changing `IFS`.
- Migrations, `db-reset`, the smoke test, and the schema check issue their SQL through SQLAlchemy constructs or literal statements in place of formatted strings. The rendered migration SQL is byte-identical.
- Exceptions that observability code swallows to protect a request are logged at debug level.
- `langfuse-worker` binds on every interface. `HOSTNAME` moved to the shared Langfuse environment anchor that both Langfuse services inherit. The worker previously bound only its container address while its health check probed loopback, so it never reported healthy and every service that waits on it stayed blocked.
- The LiteLLM gateway and the review worker resolve their AWS profile from `PLATFORM_AWS_PROFILE` and fall back to `AWS_PROFILE`. They are the two services that mount `~/.aws`. Compose reads the shell environment before `.env`, so an `AWS_PROFILE` exported in a developer shell previously reached both containers in place of the configured profile. A shell profile that resolves credentials through `credential_process` then failed every model call with `No such file or directory: 'aws'`, because the images carry no AWS CLI. A unit test now holds every service that mounts AWS credentials to the override.
- The `aurora-postgresql` module names the final snapshot `<cluster>-final-<random suffix>`, unique to each cluster. A fixed name previously made the second destroy fail, because the snapshot from the first already held it. The module now requires the random provider.
- The `dns-firewall` module writes each allowed domain with its trailing dot, the form Route 53 Resolver stores. Every plan after the first previously proposed an in-place update to both domain lists.
- The evidence object store client and `inv evidence-bucket-bootstrap` sign with the configured access keys and ignore `AWS_PROFILE` when keys are set. Compose passes the operator profile from `.env` into the activity worker, which mounts no `~/.aws`, so enabling the local MinIO evidence store previously failed every client with `ProfileNotFound`. Without keys the client still uses the default credential chain, which is the task role in AWS.
- `inv evidence-bucket-bootstrap` is registered in the task namespace. The README and the `evidence-store` module documented it, but `inv` did not list it and refused to run it.
- The platform supplies the GitHub token to git through a per-invocation credential helper that carries it in the environment, in place of embedding it in the remote URL. An embedded token was written verbatim into every execution workspace's `.git/config`, and the sandbox provisioner copies the whole workspace, `.git` included, into the agent pod that runs agent-generated code. The helper is scoped to the configured host, so a host reached through a redirect is answered with nothing, and the unscoped reset still clears any helper inherited from system or global git config. `GitAuth` renders its token as `set` or `unset`, so a log line, an exception message, or a Temporal failure payload that formats the value cannot carry it.
- An `inv scrub-workspaces` task, and a step at activity worker startup, rewrite every remote URL under `EXECUTION_WORKSPACE_ROOT` that carries an embedded credential, and report how many checkouts they rewrote. Any environment that ran an earlier release holds that credential in every workspace checkout it materialized, because a workspace is keyed by execution id and no code path deletes a finished one, so the scrub that runs when a workspace is materialized again reaches almost none of them. Operators of such an environment must run `inv scrub-workspaces`, and must rotate `GITHUB_TOKEN` and every per-repository token named in `github.yaml`, because those tokens reached the agent sandbox pod.
- The OpenHands agent server bound only its loopback, so the in-cluster driver could not reach it on the pod IP. Each sandbox now receives its own session key, which binds the server to the pod IP and requires the key on every call.
- The sandbox egress policy selected LiteLLM in `agent-sandbox`, where it does not run, and now selects it in the platform namespace.
- The local MCP gateway reached repository intelligence on the coordination service port, and now reaches it on 8120.
- The `mcp-gateway` manifest no longer sets `JIRA_ACCEPTANCE_FIELD`, which no service read.

## 0.2.0 (2026-09-14)

rebar review integration. The review gates run on the native Bedrock path with per-leg failover, every review verdict is signed with an asymmetric signature verified against a public trust root, and each authoring agent signs its plan and code change under its own rebar identity for a merge gate to verify.
- The secret store's restart rule redeploys the listed ECS services after a rotation. Its EventBridge role allowed `ssm:StartAutomationExecution` on the automation definition only, and SSM also authorizes the call against the document and the execution, so every restart was denied.

### Added

- Native Bedrock review path. The rebar review gates run reviews natively on Amazon Bedrock through a dedicated review worker, resolving each tier to a Claude primary with a Nova failover, routing through rebar's runner so prompt caching stays enabled, pricing review cost cache-aware so cached tokens are not billed at the input rate, and exporting native generations to Langfuse with the execution id and stage stamped onto each span.
- Signed review verdicts across every review stage. Plan review, code review, security review, and acceptance verification sign the canonical verdict payload with an SSHSIG signature carried in a DSSE envelope, and the gate verifies each signature against a public trust root before it accepts the verdict. A verifier holds only public keys, so it cannot forge a verdict. The evidence record carries the signing scheme, the signer key identifier, and the envelope, and enough detail to re-verify the verdict offline.
- A versioned trust-root bundle of public signer keys with per-key identifiers and validity windows, revocation of a compromised key, and an overlapping rotation window that admits a new key before the old key retires.
- A review-worker signing preflight that fails the worker at startup when signing is enabled without a usable key, a loadable trust root, and `ssh-keygen`, so a misconfiguration surfaces at startup rather than on the first review.
- A trust-root change audit. The review worker records a `review_trust_root_change` event to the audit store at startup when the loaded bundle differs from the last recorded one, naming the actor, the change summary, and the affected key identifiers.
- Authored-identity signing on the rebar backend. Each authoring agent signs the plan it produces and the code change it commits under its own rebar identity, and a merge gate verifies both signatures against the identity trust root and fails closed on an absent, tampered, or out-of-trust-root signature. The identity keyring supports trust-on-first-use genesis, signed key rotation with an overlapping window, revocation, and a keyring-change audit record. A Jira deployment has no rebar authorship substrate and does not participate.
- `REVIEW_SIGNING_ENABLED`, `REVIEW_SIGNING_KEY_PATH`, and `REVIEW_TRUST_ROOT_PATH` settings, with signing on by default, and `openssh-client` in the runtime image so `ssh-keygen` is available.
- `AUTHORSHIP_SIGNING_ENABLED`, `AUTHORSHIP_IDENTITY_ID`, and `AUTHORSHIP_SIGNING_KEY_PATH` settings for authored-identity signing.
- An acceptance-gate validation harness and a grounded labeled set. Each case carries a ticket's acceptance criteria, a completion summary, a met or unmet outcome, and a base and head file tree that the harness materializes into a temporary git repository, so the gate reviews a real change grounded at its commit the way production does. The harness scores each verdict as an agreement, a false accept, or a false block against a fixed adequacy bar and records a scorecard.
- A dedicated acceptance-verification contract. The acceptance stage judges completion-criteria coverage rather than code defects, driving the finder criterion by criterion, framing the reviewer as an acceptance auditor, and blocking on the verification's validity so a confirmed unmet criterion blocks the completion. A live scored run over the grounded set clears the adequacy bar with no false accepts and no false blocks, replacing the borrowed code-review contract that accepted incomplete work.

### Changed

- Review verdict signing is on by default and fails closed. When signing is enabled but the key or trust root is not configured, a review stage raises rather than downgrading to the symmetric HMAC path. Setting `REVIEW_SIGNING_ENABLED` to false selects the HMAC path for local development.
- Database migrations apply only through the `db-migrate` container. `inv db-migrate` and `inv db-reset` run that container, which mounts the working-tree migrations so the applied scripts match the checkout, and a guard in the migration environment refuses `alembic upgrade`, `downgrade`, and `stamp` on the host so a host run cannot advance the database past the revisions the container carries.

### Fixed

- Code authorship is signed at promotion over the final commit, so a signature bound to the promoted change survives a CI-repair recommit that advances the branch head. The merge gate verifies the plan and code signatures on every promotion path.
- The activity worker runs an authored-identity signing preflight at startup. When the capability is active it refuses to start unless `ssh-keygen`, the signing key, and the configured identity's trust root are usable, so a misconfiguration surfaces at startup rather than on the first signed run.
- `inv operator-done` rewrites the container mount roots in `SOURCE_CONTROL_LOCAL_ROOT` and `SOURCE_CONTROL_LOCAL_ARTIFACTS_ROOT` to the host directories that back the compose mounts, so the host command verifies artifacts at the checkout the workers wrote.

## 0.1.0 (2026-09-11)

First versioned release of the platform. This version makes the ticket tracker and the source-control target pluggable behind two orthogonal contracts, bounds concurrent runs with a platform admission cap, and re-grounds a run that discovers a cross-ticket dependency during planning on both the rebar and Jira backends. A deployment that configures neither backend behaves exactly as before.

### Added

- `TicketBackend` contract and a `build_ticket_backend` factory that defaults to Jira, threaded through every orchestration call site.
- A rebar ticket-store backend that reads tickets, transitions status, records linkback and approval, and resolves the platform's logical lifecycle stages to the store's own statuses.
- A `build_git_host` selection defaulting to GitHub and a `LocalGitHost` that commits locally, performs no push, and opens no pull request, leaving a promoted branch and a summary and patch artifact.
- A provider-neutral `PublishResult` carrying source-control artifacts only, with backend-neutral publish discovery.
- An operator done command for the local source-control backend, authenticated, idempotent, and audited.
- A flag-driven `inv` poll over the rebar tickets branch with a lossless cursor, an authenticated reader identity, field redaction, and per-invocation auditing.
- Rebar ticket-store credential isolation config that separates read-only polling and write roles from the evidence and audit writers.
- A `tickets` per-environment config file, version-gated like the other config files.
- Reusable `vpc-endpoints`, `ecr`, `cloudtrail`, and `bedrock-iam` Terraform modules that own the shared VPC endpoints, the container registry, the audit trail, and the `bedrock:InvokeModel` policy, each toggleable so an account reuses infrastructure it already has.
- A `bedrock-jumphost-fargate` Terraform module that provisions an ephemeral ECS Exec hop to the private Bedrock endpoint, with least-privilege task roles, a KMS-encrypted and audited exec channel, and a hardened exec-log bucket, consuming the shared endpoints and registry as inputs.
- A `private-bedrock` composition root that wires the network, endpoints, registry, audit trail, and jumphost into one apply, working from zero or against an existing VPC through tfvars, with greenfield and existing-network examples.
- A `jumphost-base` container image and an `inv publish-jumphost-image` task that builds and pushes it to the account ECR repository.
- An execution orphan reconciler that runs at the start of every intake pass and returns a non-terminal execution to a terminal state when its workflow is missing or closed, so the platform concurrency cap reclaims slots held by runs whose workflow no longer exists. The grace window is configurable through `EXECUTION_ORPHAN_GRACE_SECONDS`.
- Cross-ticket dependency discovery. When `DEPENDENCY_DETECTION_ENABLED` is set, a run detects during planning whether its change depends on another in-flight run through file-impact overlap and unresolved-symbol references, records the dependency on the ticket store, pauses on the dependency seam without holding compute, and resumes when the blocking ticket reaches certified terminal completion. On resume it re-captures its base and re-plans, then re-verifies against the runs still in flight, bounded by a re-plan attempt cap and a dependency-cycle guard. Detection is inactive for a backend without the file-impact capability, and the attempt cap is configurable through `DEPENDENCY_REPLAN_ATTEMPTS`.
- Backend-neutral cross-ticket dependency discovery. The per-run predicted touch set moves to a platform-owned `run_file_impact` table read through a `FileImpactStore`, so overlap detection no longer depends on the ticket backend. The `DependencyBackend` capability narrows to the graph operations `link`, `declared_dependencies`, and `dependents`, plus a `dependency_graph_active` predicate, and the Jira adapter implements it over Jira issue links. A run publishes its touch set on any backend and detects, records, and pauses only when its backend reports the graph active. A Jira project activates the graph by configuring `dependency_link_type` with an existing Jira link type; a project that leaves it unset publishes its touch set but records nothing and pauses on nothing.

### Changed

- The implementation token budget counts billable (non-cached) tokens rather than total tokens, so prompt-cache reads no longer count against the cap. A run that reuses a large cached context is bounded by cost and call-count caps instead of tripping the token cap on cache reads.
- The security scan and source-control mediators guard against the backend-neutral source-control allowlist rather than the GitHub credential file, so a deployment targeting a local git folder admits its repositories without a `github.yaml`.
- The jumphost connect script drives the Fargate run-task and ECS Exec port-forward flow, resolving the cluster and task definition from SSM parameters, and preserves the `-n`, `-e`, `-p` interface the connectivity provider calls.
- Ticket write-back routes through the configured ticket backend under a write contract with per-project credentials, ticket-ownership validation, least-privilege scopes, idempotent concurrency, and an audit record naming actor, backend, project, ticket, and run id.
- Terminal completion from a merged or closed ticket status proceeds only after authenticated status provenance, a matching publish result, passed gates, and verified branch and artifact identifiers, with a recorded precedence rule when ticket status and source-control state disagree.

### Fixed

- Planning-stage context retrieval derives symbol and file focus terms from the ticket title and description instead of sending the natural-language title as the focus. The repository-intelligence providers key on a symbol or file name, so the title matched nothing and the context package returned no impacted files, symbols, or references. The context service now extracts code-like identifiers and repository file paths from the title and description, queries the index for each, and unions the results, so the predicted touch set reflects the files a run is expected to touch and cross-ticket dependency detection operates on populated data. A single-token focus with no description keeps the prior single-symbol behavior.
- The pre-PR issue recheck normalizes the fresh ticket through the same backend that produced the stored intake payload, so a rebar run no longer pauses with a false execution-invalidating verdict from comparing a rebar-shaped stored payload against a Jira-normalized fresh payload. Each ticket backend owns a `recheck_payload` method that returns the comparison payload in its intake shape.
- The promotion policy reads its project and repository allowlists and its CI requirement from the decision input rather than hardcoded sets, and the policy mediator fills those from the configured ticket and source-control backends. A local source-control run whose backend runs no continuous integration is no longer denied for `ci_not_successful`, `repository_not_allowlisted`, or `jira_project_not_allowlisted`, while a deployment that supplies no input allowlists keeps the previous defaults.
- Intake starts a local source-control run with the await-close step enabled so the run parks at `AWAITING_PR_CLOSE` until the operator done command signals completion, which transitions the ticket to its terminal status. Without this a local run stopped at branch promotion and its ticket never reached the closed status.
